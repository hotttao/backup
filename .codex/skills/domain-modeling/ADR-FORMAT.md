# ADR 文档规范格式
所有架构决策记录（ADR）统一存放于 `docs/ddd/adr/` 目录，采用连续数字编号命名：`0001-标识名.md`、`0002-标识名.md`，以此类推。

采用懒创建机制，仅在需要撰写第一条 ADR 时，再新建 `docs/ddd/adr/` 文件夹。

## 标准模板
```md
# {决策简短标题}

{1-3句话：说明业务背景、最终敲定的方案、做出该选择的核心理由}
```

仅以上内容为必填项，一份ADR可以只包含一段文字。ADR的核心价值是记录**已做出的决策**以及**决策背后的原因**，而非堆砌固定分栏。

## 可选补充板块
仅当该板块能提供实际参考价值时才添加，绝大多数ADR无需填写。
- **状态元数据**（可选值：proposed 待提议 / accepted 已采纳 / deprecated 已废弃 / superseded by ADR-NNNN 被编号NNNN的ADR替代）：适合需要反复复盘调整的决策
- **备选方案考量**：仅当被否决的方案具备留存参考价值时填写
- **衍生影响**：仅当存在不易察觉的后续连锁影响，需要明确标注时填写

## 编号规则
遍历 `docs/ddd/adr/` 目录，读取当前已存在文件的最大编号，在此基础上加一作为新 ADR 编号。

## 何时需要新建ADR文档
必须同时满足以下全部3个条件：
1. **难以回退**：后续推翻该决策的改造成本较高
2. **无上下文难以理解**：后续维护人员查看代码时，会产生疑问“当初为什么要这么设计？”
3. **经过多方权衡取舍**：存在多种可行替代方案，基于特定理由选定当前方案

若决策可以轻易修改，则无需记录，直接调整即可；若设计逻辑显而易见，后人不会产生疑问，也无需记录；若不存在其他可选方案，仅需简单说明“采用常规方案”，不必单独生成ADR。

### 需要记录的决策类型
1. **整体架构选型**
例：采用单仓库架构；写入模型采用事件溯源、读取模型投影至PostgreSQL。
2. **限界上下文之间的集成通信方案**
例：订单域与账单域通过领域事件通信，而非同步HTTP调用。
3. **存在锁定成本的技术选型**
数据库、消息队列、身份认证服务、部署环境等。并非所有第三方库都需要记录，仅记录替换成本极高（如需耗费一个季度改造）的核心组件。
4. **领域边界与权责划分**
例：客户数据归属客户域，其他域仅通过ID关联引用。明确划定“不可做”的约束，和“允许做”的规则同等重要。
5. **刻意摒弃常规方案的设计**
例：放弃ORM框架、手写原生SQL，原因是XXX。这类设计容易被后续工程师误当作bug修复，记录后避免重复返工。
6. **代码中无法直观体现的硬性约束**
例：合规要求禁止使用AWS；对接第三方合作方接口，响应耗时必须控制在200毫秒以内。
7. **否决方案存在隐性理由**
若对比GraphQL后因细微因素选择REST接口，需记录取舍逻辑，防止数月后其他开发人员再次提出改用GraphQL。
