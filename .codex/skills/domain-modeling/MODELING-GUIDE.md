# 从发现到领域模型

仅在从业务讨论、需求或实现中提炼领域模型时读取本文件。

## 1. 先确定建模命题

开始前明确：

- 业务目标、流程起止点和明确排除项；
- 当前参与的角色、团队、服务和外部系统；
- 本次描述当前实现（as-is）还是目标设计（to-be）；
- 权威事实来源及其优先级；
- 需要更新哪些上下文，哪些上下文仅作为外部依赖。

不得把当前实现和目标设计混写。代码可以证明 as-is，不能否定业务方已明确采纳的 to-be；业务设想不能伪装成已经实现的事实。

## 2. 从头脑风暴获取建模输入

优先使用事件风暴的结果导向方式：先按时间顺序识别业务人员关心的已发生事实，再反推命令。

必须尽量获得：

| 输入 | 最少需要知道的内容 |
|:---|:---|
| 范围 | 业务目标、起点、终点、排除项、as-is/to-be |
| 领域事件 | 已发生的业务事实、顺序、正常与异常分支 |
| 命令 | 执行者、目标、所需数据、前置条件、成功事件、失败结果 |
| 执行者 | 业务角色或系统角色，不记录具体姓名 |
| 查询 | 为命令服务的数据，以及不产生事件的独立查询 |
| 候选名词 | 从事件、命令、角色和查询中提取的业务概念 |
| 规则 | 必须、只能、不能、至少、最多、当……时等约束 |
| 边界场景 | 重复、并发、越权、取消、超时、部分成功、晚到结果 |
| 证据与疑问 | 来源、确认状态、冲突、待确认问题和负责人 |

事件使用完成时业务语言，如“订单已支付”，不要把 HTTP、队列、缓存等技术动作写成领域事件。命令使用业务动词，如“支付订单”。

如果需要保留工作坊中间结果，按 [DISCOVERY-FORMAT.md](DISCOVERY-FORMAT.md) 写入 `docs/ddd/discovery/`。已有用户故事、用例或需求系统承担原始事实来源时，不要求长期维护重复的 Discovery 文档。

## 3. 将输入转换为领域模型

### 3.1 统一语言

- 合并同义词并选择一个标准词，其他名称记为禁用替代词；
- 拆分同名异义词，并明确各自所属限界上下文；
- 确定中文名、英文全称及代码名；
- 定义只回答“是什么”，行为和规则放进 Domain 文档。

### 3.2 分类候选名词

不要将名词直接等同于实体或数据库表。逐项判断：

- 有稳定身份和生命周期：实体；
- 只由值定义、相同值可替换：值对象；
- 只描述其他对象：属性；
- 表示实体在场景中的身份：角色；
- 关系自身拥有属性、状态或历史：关联实体；
- 代表可维护的业务分类：类别；
- 包含业务决策但不自然属于某个实体：领域服务或操作；
- 跨聚合、事务或外部系统协调：Workflow；
- 只为展示和检索组织数据：读模型。

名词化的动词可以成为实体，例如需要身份、状态和生命周期的 Payment。

### 3.3 建立关系

对任意对象 A、B，分别询问 A 对 B、B 对 A 的最小和最大数量，得到 `0..1`、`1..1`、`0..*`、`1..*`。每条关系必须写明两端角色和业务语义。

- 一对一不自动合并；根据业务关注点、生命周期和变化原因判断；
- 多对多关系有属性、有效期或历史时，提升为关联实体；
- 自关联必须标明父/子、上级/下级等角色；
- 同一对对象存在多种关系时，分别命名角色；
- 图上 `{}` 约束必须同步进入业务规则表。

### 3.4 使用 UML 类图表达模型

当 Domain 包含多个对象或任意对象关系时，按 [UML-CLASS-DIAGRAM-GUIDE.md](UML-CLASS-DIAGRAM-GUIDE.md) 绘制类图。类图必须表达：

- 使用统一语言命名的领域对象；
- 理解身份、关系和规则所需的关键属性；
- 对象承担的业务操作；
- 关联的业务语义、两端角色和双端多重性；
- 多对多关系产生的关联实体；
- 自关联和同类对象间不同关系；
- 与业务规则表对应的约束编号。

图后解释容易误读的关系。类图不画全部数据库字段和技术类型，也不能代替业务规则表与词汇表。

### 3.5 识别操作、规则和状态

沿每个命令走查：

```text
执行者 -> 所需查询 -> 目标对象/聚合 -> 前置规则 -> 领域操作 -> 状态变化 -> 领域事件
```

每条重要规则分配稳定编号，并记录场景、条件、规则正文、所有者、执行时机、违反结果和证据。涉及生命周期时建立状态转换表或状态图，覆盖终态、重复命令、并发命令和晚到事件。

### 3.6 模块、限界上下文和 Context Map

先按高内聚、低耦合将对象组织为模块；当语言、规则、所有权或变化原因出现边界时，划分限界上下文。服务和数据库是实现线索，不自动等于限界上下文。

Context Map 必须记录上下文职责、拥有的业务事实、上游/下游关系、集成方式、公开语言和一致性预期。跨上下文传递 ID、DTO、命令或事件，不共享可修改的领域实体。

### 3.7 聚合

聚合是事务一致性边界。属于同一聚合通常因为：

- 必须原子维护同一条不变量；
- 子对象不能绕过聚合根独立修改；
- 生命周期完全依附聚合根。

外键、联表查询、同页展示、接口一次返回都不能证明同一聚合。跨聚合只引用 ID；跨服务不建立数据库外键。优先小聚合，跨聚合一致性由 Workflow 协调。

### 3.8 Domain Event 与 Workflow

Domain Event 是聚合已发生的业务事实。需要通知其他上下文时，再通过明确契约转换为集成事件，不默认复用内部事件结构。

出现跨聚合、跨事务、跨服务、外部副作用、异步、重试、补偿或恢复时，按 [WORKFLOW-FORMAT.md](WORKFLOW-FORMAT.md) 建立 Workflow。单聚合状态机、普通 CRUD、纯查询和 DTO 转换不创建 Workflow。

## 4. 模型验证技巧

### 命令走查

每个命令都应能回答：谁发起、作用于谁、需要什么、谁判断规则、改变什么、产生什么事件、失败后看到什么。

### 边界场景

至少测试零个/一个/多个、重复、并发、越权、取消、超时、部分成功、历史数据和规则变化。

### 双向追踪

- 从命令追到聚合、规则、事件和 Workflow；
- 从事件反查产生者和消费者；
- 从表、接口、定时任务和消费者反查是否有遗漏能力；
- 从每条规则反查所有者、执行点和测试位置。

### 抽象检验

只抽象业务人员承认且规则稳定的共性，不因字段或代码相似而泛化。无法用真实场景解释的抽象保留为候选，不写进正式模型。

## 5. 完成检查

- 术语唯一且归属明确；
- 所有输入都有正式归属、明确排除或待确认状态；
- 实体身份、值对象相等性、关系角色和多重性完整；
- 需要类图的 Domain 已使用 UML 表达，并能通过命令走查；
- 规则有编号、所有者、执行时机和违反结果；
- 聚合根和原子不变量明确；
- 生命周期和并发语义明确；
- 每个写能力和领域事件完成 Workflow 判定；
- Context、Domain、Workflow 和 Context Map 相互一致；
- 未确认推断没有进入正式领域文档。
