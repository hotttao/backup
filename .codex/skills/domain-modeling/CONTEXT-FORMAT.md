# CONTEXT.md 文档规范

`docs/ddd/<service-or-context>/CONTEXT.md` 是一个限界上下文内统一语言的权威词典。它只定义概念是什么、与相近概念如何区分，不保存字段、流程、代码位置、技术决策或变更历史。

多上下文系统的边界和依赖另见 [CONTEXT-MAP-FORMAT.md](CONTEXT-MAP-FORMAT.md)。

## 标准模板

```md
# {限界上下文名称}

{一到两句话说明该上下文的业务范围、拥有的事实和存在意义。}

## 业务术语词典

**订单（Order，代码名：`Order`）**

客户确认购买后形成、由本上下文跟踪履约前状态的业务承诺。

_区别_：购物车是购买意向，不是订单；支付是针对订单发生的资金行为。

_禁用替代词_：Purchase、transaction、交易单。

**客户（Customer，代码名：`CustomerId`）**

提交订单的个人或企业主体；本上下文只保存其身份引用，不维护客户资料。

_禁用替代词_：Client、buyer、account。
```

## 编写规则

- 每个术语给出标准中文名、英文全称和推荐代码名；
- 定义最多一到两句话，只回答“是什么”和本上下文拥有哪部分语义；
- 容易混淆时添加“区别”，明确与相近概念的边界；
- 同义词选一个标准词，其余放入“禁用替代词”；
- 同一个词在不同 Context 含义不同时分别定义，不创建含糊的全局定义；
- 只收录业务专属词汇，不收录超时、DTO、Repository 等通用技术词；
- 术语可按模块分组，但不要把 CONTEXT 写成需求文档；
- 规则、操作和状态放 Domain，跨边界协作放 Workflow，事实来源与未决项放 Discovery；
- 新术语必须与 Context Map 和相关 Domain 命名一致。

## 创建与定位

1. 存在 `docs/ddd/CONTEXT-MAP.md` 时，根据映射定位所属 Context；
2. 单上下文仓库可以只维护一个根 `docs/ddd/CONTEXT.md`；
3. 两者都不存在时，敲定第一个术语和上下文边界后再懒创建；
4. 无法判断术语归属，或发现同名异义会改变边界时，列出差异并向用户确认。
