# 008 聚合、泛化与限界上下文：从项目代码理解 DDD

> 本文只讨论三个容易混淆的概念，并用 `tmp/ddd` 下的两个 Go 项目说明它们分别解决什么问题。
>
> 先给结论：**限界上下文是模型边界，聚合是一致性边界，泛化是类型抽象关系**。前两个是 DDD 的核心概念；“泛化”主要来自 UML/面向对象建模，并不是 DDD 的核心战术模式。

## 一、三个概念不在同一个层次

| 概念 | 要解决的问题 | 在项目中的例子 |
| --- | --- | --- |
| 限界上下文（Bounded Context） | 哪套业务语言和规则在哪个范围内有效 | `trainer`、`trainings`、`users`；`Catalog`、`Orders` |
| 聚合（Aggregate） | 哪些对象必须作为一个整体保持一致 | `Hour`、`Training`、`Order` + `ShopItem` |
| 泛化（Generalization） | 多个类型是否存在稳定的 `is-a` 关系 | 技术上的 `EventSourcedAggregateRoot` 复用；不是跨上下文共享模型的理由 |

可以用三个边界记忆：

```text
限界上下文 = 业务语言边界
聚合       = 事务一致性边界
泛化       = 类型抽象边界
```

## 二、限界上下文：同一个词，不一定是同一个模型

`wild-workouts-go-ddd-example` 的核心目录是：

```text
internal/
├── trainer/
├── trainings/
└── users/
```

它们可以理解为三个限界上下文。

### 2.1 Trainer 上下文中的 Hour

在 `internal/trainer/domain/hour/hour.go` 中，`Hour` 表示教练排班中的一个可预约时间段：

```go
type Hour struct {
    hour         time.Time
    availability Availability
}
```

它关心的是：

- 时间是否在允许的未来范围内；
- 是否是整点；
- 当前是否可预约；
- 已预约的时间能否被设置为不可用。

因此 `Available`、`NotAvailable`、`TrainingScheduled` 是这个上下文里的核心语言。

### 2.2 Trainings 上下文中的 Training

在 `internal/trainings/domain/training/training.go` 中，`Training` 表示已经成立的一场训练：

```go
type Training struct {
    uuid string
    userUUID string
    userName string
    time time.Time
    notes string
    proposedNewTime time.Time
    moveProposedBy UserType
    canceled bool
}
```

这里的 `time` 已经不是“教练是否开放的资源”，而是训练实际发生的时间。它关心：

- 训练是否已取消；
- 训练能否免费取消；
- 谁提出了改期；
- 另一类用户能否批准改期；
- 谁能查看这场训练。

同样是 `time.Time`，在两个上下文里的业务含义完全不同：

```text
Trainer.Hour.time     = 可预约资源的时间
Trainings.Training.time = 已成立训练的时间
```

DDD 不要求把它们抽成一个全局的 `ScheduleTime` 模型。模型应该服务于上下文内的规则，而不是追求全局字段复用。

### 2.3 User 也不应该只有一个全局实体

Trainings 上下文只定义了自己需要的用户信息：

```go
type User struct {
    userUUID string
    userType UserType
}
```

它只需要判断“是谁”和“是教练还是学员”，不需要 Users 上下文中的密码、头像、注册时间等字段。

因此跨上下文传递的通常是 ID、DTO、事件或快照，而不是共享一个可被所有服务直接修改的领域实体：

```text
Users 上下文 ──用户身份事件/DTO──> Trainings 上下文
```

### 2.4 微服务不等于限界上下文

部署边界和领域边界是两个问题。`go-food-delivery-microservices` 中：

- `catalogwriteservice` 和 `catalogreadservice` 可以看作 Catalog 上下文的写端和读端；
- `orderservice` 是 Orders 上下文；
- 读写拆成两个进程，不代表业务模型自动变成两个上下文。

判断限界上下文，要看业务语言、规则和模型是否不同，而不是只看进程或数据库数量。

## 三、聚合：为了业务一致性而一起修改

聚合是一个由实体和值对象组成的集合，并且有一个对外的入口——**聚合根**。它的关键问题不是“包含多少对象”，而是：

> 哪些不变量必须在一次业务操作完成时立即成立？

### 3.1 Order 是 Orders 上下文中的聚合根

在 `go-food-delivery-microservices/internal/services/orderservice/internal/orders/models/orders/aggregate/order.go` 中：

```go
type Order struct {
    *models.EventSourcedAggregateRoot
    shopItems []*value_objects.ShopItem
    paid bool
    submitted bool
    completed bool
    canceled bool
}
```

它的结构可以画成：

```text
Order 聚合
└── Order                 聚合根
    ├── paid / submitted / canceled
    └── ShopItem           值对象
        ├── title
        ├── quantity
        └── price
```

订单创建时必须至少包含一个商品项：

```go
if shopItems == nil || len(shopItems) == 0 {
    return nil, domainExceptions.NewOrderShopItemsRequiredError(...)
}
```

这就是聚合保护的不变量。外部不应直接修改订单内部字段，而应该通过 `UpdateShoppingCard`、`Submit`、`Pay`、`Cancel` 等业务行为改变状态。事件溯源场景下，`AggregateStore` 也以整个 `Order` 聚合为加载和保存单位。

### 3.2 为什么 Product 不直接放进 Order

`Product` 属于 Catalog 上下文，订单只保存下单时的商品快照 `ShopItem`：

```text
Catalog.Product ──下单时复制标题/价格──> Orders.ShopItem
```

这样商品后续涨价不会改变历史订单。跨上下文共享 `Product` 实体，会让 Orders 依赖 Catalog 的内部状态，也会破坏各自的模型自治。

### 3.3 Hour 也是一个小聚合

`Hour` 只有一个实体和一个 `Availability` 值对象，但仍然可以是聚合：

- 已预约时不能直接变为不可用；
- 只有可用时间才能预约；
- 没有训练时才允许取消预约。

聚合不一定“大而全”。通常应该尽量小，以减少锁竞争、事务范围和并发冲突。

## 四、泛化：不要把技术复用误认为业务模型

泛化表达的是稳定的 `is-a` 关系，例如：

```text
Payment
├── WeChatPayment
└── AlipayPayment
```

只有当子类型确实可以替代父类型，并且拥有共同的业务契约时，泛化才有意义。

### 4.1 项目中的技术泛化

`Order` 嵌入了：

```go
*models.EventSourcedAggregateRoot
```

它复用了聚合 ID、版本、未提交事件、`Apply` 等事件溯源能力。这是技术基础设施层面的复用。不能因此把“事件溯源聚合根”当成业务父类；在业务语言里，`Order` 仍然只是一个订单聚合。

### 4.2 不要因为字段相同就泛化

`trainer.Hour` 和 `trainings.Training` 都有时间字段，但它们不是同一种业务对象：

```text
Hour      ≠ Training
```

同理，Trainings 中的 `User` 也不应继承 Users 上下文的完整用户实体。跨上下文的重复字段是可接受的，模型自治比消除重复更重要。

## 五、三者如何协同

```text
Wild Workouts
├── Trainer 限界上下文
│   └── Hour 聚合
│       └── Availability
├── Trainings 限界上下文
│   └── Training 聚合
│       └── UserType
└── Users 限界上下文
    └── 用户身份模型
```

一次“预约训练”可能跨越上下文：Trainer 先把 `Hour` 从可用变为已预约，Trainings 再创建 `Training`。这两个聚合不应该被强行合并为一个跨服务大聚合；跨上下文协作可以通过应用服务、RPC、领域事件和补偿机制完成。

可以用三个问题做设计判断：

1. 这个词在不同业务场景中的含义和规则是否不同？不同的话，考虑拆分限界上下文。
2. 哪些数据必须在一次操作中立即一致？把它们放入同一个聚合，并通过聚合根修改。
3. 两个类型是否真的存在稳定的 `is-a` 关系？如果只是字段相似，不要为了 DRY 泛化。

> 如果这里的“泛化”原本想指“泛型”，那是 Go 的语言特性，例如 `AggregateStore[T]`；它帮助复用存储代码，但不属于 DDD 的领域概念。
