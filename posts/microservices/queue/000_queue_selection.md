这个系列我们做一次消息队列的选型，了解一下现在市面上主流的消息队列的架构、功能和局限。

<!-- more -->

## 1. 什么需要消息系统

消息系统通常承担五种职责：

1. **解耦**：生产者不需要等待消费者在线；
2. **削峰**：用积压吸收生产与消费之间的速率差；
3. **异步任务**：把耗时工作从请求链路中移出；
4. **事件分发与回放**：一份事件供多个系统独立读取；
5. **低延迟通信**：进程之间快速传递数据。

这五类需求并不等价。任务队列关心确认、重投和死信；事件日志关心保留、位点和回放；通信库关心连接与延迟，但通常不负责持久化和故障恢复。先确定模型，再比较产品。

如果只需要进程内异步，内存 Channel 往往足够；如果只为解决“数据库提交后可靠发事件”，还要同时设计 Transactional Outbox，而不是期待消息组件替数据库事务兜底。

### 1.1 消息系统的核心实现
1. 控制面采用什么组件和协议达成数据一致性
2. queue 支不支持分区、分区 router 在何处实现、顺序性如何保证、分区重分配如何实现
3. queue 支不支持多副本、多副本如何达成数据一致性、故障恢复流程
3. 消费者，支不支持消费者组、消费者协调过程、如何支持消费者 rebanace
4. 消费者协调数据保存在哪、消费进度数据保存在哪


## 2. 三种基本模型

| 模型 | 核心状态放在哪里 | 主要能力 | 根本局限 |
|---|---|---|---|
| Broker 任务队列 | Broker 保存待处理消息和确认状态 | 路由、确认、重投、死信 | 大量历史回放通常不是第一目标 |
| 分布式日志 | Broker 保存追加日志和消费位点 | 高吞吐、保留、回放、多订阅 | 顺序和并行度受分片边界约束 |
| Brokerless 通信库 | 应用进程和连接缓冲区 | 低延迟、灵活通信拓扑 | 持久化、复制、发现和恢复由应用建设 |

产品名称相似，不代表处于同一抽象层。选型前必须先问：我们是在选择一套服务，还是选择一个用来搭建服务的通信库？

## 3. 决定选型的十个问题

### 3.1 什么绝对不能丢

先定义故障模型：进程崩溃、单机损坏、可用区中断，还是地域灾难。

还要分别定义：

- 未确认消息允许丢失吗；
- 已确认消息允许丢失吗；
- 消息保存到内存、操作系统缓存、磁盘或多个故障域中的哪一步才算成功；
- 为避免丢失，能否接受副本不足时暂停写入。

本质上，这是在一致性、可用性和延迟之间选择边界。

### 3.2 能否接受重复

网络超时不能证明消息没有成功。消息可能已经提交，只是响应丢了；生产者重试后就会出现重复。消费者也可能在业务完成后、确认之前崩溃，从而再次收到同一消息。

因此，可靠系统的基本假设通常是“至少一次 + 业务幂等”，而不是把一次网络响应理解成端到端精确一次。每条消息应有稳定的业务事件 ID，关键消费者应使用唯一键、Inbox 或状态机防重。

### 3.3 顺序的业务边界是什么

全局顺序会把系统压缩成单通道，是吞吐和可用性的上限。更常见的要求是同一订单、账户或设备内有序。

必须同时检查：

- 同一业务 Key 是否始终进入同一分片；
- 多生产者并发时，谁定义先后；
- 多消费者和异步处理是否改变完成顺序；
- 失败重试能否越过后续消息；
- 扩分片后 Key 是否漂移。

Broker 的存储顺序不等于业务完成顺序。

### 3.4 消息是任务还是历史

消费完成后删除，适合任务队列；保留日志并记录每个订阅的位点，适合事件回放。需要明确最长保留时间、最大积压量、回放能力、消费位点过期，以及按时间、容量或 Key 清理的语义。

### 3.5 峰值和积压怎样被消化

平均吞吐量参考价值有限。容量设计至少需要峰值写入速率、消息大小、消费者处理能力和最长故障时间：

```text
最大积压量 ≈ 峰值生产速率 × 最长不可消费时间
恢复能力要求：恢复期消费速率 > 恢复期生产速率
```

达到容量上限后，系统究竟阻塞生产者、拒绝写入、淘汰旧消息还是耗尽内存，往往比峰值 Benchmark 更重要。

### 3.6 如何横向扩展

副本用于容错，分片用于扩吞吐，两者不能混为一谈。要确认**分片是否自动完成**、**热点 Key 是否受单分片限制**、**分片数是否限制消费并行度**，以及**扩缩容搬迁是否影响顺序和尾延迟**。

### 3.7 消费失败如何收敛

重试不是越多越可靠。无限重试会形成热循环，一条毒消息还可能阻塞整个顺序通道。需要统一定义超时、退避、最大次数、死信、人工修复和重新驱动流程。

如果业务要求严格顺序，就必须在“等待失败消息恢复”和“跳过它继续处理”之间明确选择。

### 3.8 数据契约如何演进

消息会长期存在并被不同版本的消费者读取。应明确序列化格式、Schema 所有者、向前/向后兼容规则，以及无法反序列化的消息如何隔离。否则消息系统越稳定，错误契约传播得越远。

### 3.9 谁来运营它

需要评估滚动升级、容量、多租户隔离、安全、配额、监控、备份恢复和故障演练。团队必须能区分控制面、数据面和客户端问题，而不只是会查看进程是否存活。

### 3.10 单集群故障还是跨地域灾难

单集群副本主要解决节点或可用区故障；跨地域复制通常有独立链路和独立一致性语义。必须为灾备定义 RPO、RTO、切换入口、消费位点迁移、重复范围，以及回切时如何处理两地分叉的数据。

## 4. 用一个临界场景检查提交语义

所有组件都应能回答下面这条时间线：

```text
T1 生产者发送消息 M
T2 接收方在本地接受 M
T3 M 被写入持久介质
T4 M 到达其他故障域中的副本
T5 系统认定 M 已提交
T6 系统返回成功
T7 生产者收到成功
```

最关键的问题只有两个：系统把 T5 定义在哪一步；发生故障后，谁有权决定唯一的有效历史。

如果 T6 发生在 T4 之前，故障切换可能丢掉已经向客户端确认的消息；如果必须等待多个副本，副本不足时就只能增加延迟或停止写入。若故障发生在 T5 和 T7 之间，结果对客户端未知，必须用相同业务 ID 重试并接受去重。

恢复的旧节点不能自行把独有尾部重新发布。它必须服从当前有效历史：删除冲突尾部、补齐缺失数据，再重新成为可用副本。否则系统会产生双主和消息“复活”。

## 5. 架构图完整性检查

一张生产架构图至少应画出六类角色；不存在的角色也应明确标注由谁承担：

1. **客户端层**：生产者、消费者、连接入口和服务发现；
2. **路由层**：Topic、Exchange、Subject、分片或业务 Key 如何定位数据；
3. **数据面**：接收写入、保存消息、投递消息的节点；
4. **一致性机制**：Leader、Follower、法定副本、任期或同步集合；
5. **控制面**：元数据、成员关系、选主、分片所有权；
6. **消费状态**：确认、消费位点、待确认集合或订阅游标。

还应标出本地磁盘、共享存储或独立存储集群，并区分实线数据流与虚线控制流。只有生产者到 Broker 的箭头，不是一张完整的生产架构图。

## 6. 主流候选的定位

| 组件 | 本质定位 | 优先考虑的场景 | 主要边界 |
|---|---|---|---|
| Kafka | 分区事件日志 | 数据库变更分发、集中收集日志、实时计算、让新系统重放历史事件 | 需要规划分片、积压和消费组 |
| RabbitMQ Queue | 路由型任务队列 | 按规则投递任务、逐条确认、消息过期、优先任务和临时队列 | 单条 Queue 不会自动分区；关键任务需选择 Quorum Queue |
| RabbitMQ Stream | 追加事件日志 | 多订阅、Offset 回放和 Super Stream 分区吞吐 | 与 Queue 的确认、保留和消费模型不同 |
| RocketMQ | 面向业务事件的分布式消息系统 | 顺序、事务、延时和交易事件 | 部署模式会改变可靠性边界 |
| Pulsar | 存算分离的多租户事件系统 | 海量 Topic、长积压、独立扩缩存储与服务 | 组件较多，运维门槛较高 |
| NATS JetStream | 轻量持久消息与事件流 | 云原生、低延迟、中等规模持久消息 | 大规模分片需要主动设计 |
| Redis Streams | Redis 内的追加日志数据结构 | 已有 Redis 的轻量任务和事件流 | 可靠性与扩展受 Redis 模型约束 |
| ActiveMQ Artemis | JMS 与多协议企业消息 Broker | 传统企业集成、多协议和事务 | HA 与集群横向路由是两套机制 |
| ZeroMQ | Brokerless 通信库 | 极低延迟、进程间通信、自定义拓扑 | 不自带持久化、复制、消费位点和运维控制面 |

### 6.1 事件流与分布式日志

**事件**表示已经发生的事实，例如“订单已创建”“商品库存已扣减”“用户修改了手机号”。事件通常不应被修改，而是继续追加新的事件表达后续变化。

**事件流（Event Stream）**是持续产生的一系列事件。比如一个电商平台每天产生订单、支付、发货和退款事件，各系统按自己的目的持续读取：

- 风控系统检查异常交易；
- 推荐系统更新用户偏好；
- 数据仓库生成经营报表；
- 通知系统发送短信。

**分布式日志**是保存事件流的一种模型。消息按顺序追加到多个分片中，消费者记录自己读到的位置。消费并不会立即删除消息，所以其他消费者和后来接入的系统仍能读取。

它的核心价值不是“异步”本身，而是把事件保存成一段可以被多个系统独立读取的历史。

### 6.2 CDC：把数据库变化变成事件

CDC 是 **Change Data Capture，变更数据捕获**。它读取数据库的事务日志，把插入、更新和删除转换成消息。

例如订单服务把订单状态从“待支付”改为“已支付”，CDC 可以产生一条变更事件，供搜索、库存、报表和推荐系统更新自己的数据，而不必让这些系统直接查询订单数据库。

实用场景包括：

- 把业务数据库实时同步到数据仓库；
- 更新 Elasticsearch 等搜索索引；
- 拆分单体系统时，把旧数据库的变化同步给新服务；
- 让缓存、风控和报表响应数据变化。

CDC 的局限是它看到的首先是“数据库某行发生变化”，不一定天然等于完整的业务语义。字段含义、事件顺序、Schema 演进和重复消费仍要设计。

### 6.3 日志聚合：把分散日志集中起来

这里的“日志”是应用和服务器产生的运行记录，例如访问日志、错误日志和审计日志，不是数据库事务日志。

**日志聚合**就是把成百上千个服务实例的日志先汇入统一消息系统，再由下游写入搜索或分析平台：

```text
应用实例 → 消息系统 → 日志存储 / 搜索平台 / 告警系统
```

这样做可以吸收突发日志流量，并把“产生日志”和“索引日志”解耦。即使搜索平台短暂变慢，应用也不需要同步等待它。

### 6.4 流处理：数据到达时持续计算

传统批处理是先积累一天数据，再统一计算；**流处理**是在事件持续到达时不断更新结果。

例如：

- 统计最近五分钟每个接口的错误率；
- 发现一分钟内连续多次支付失败的账户；
- 实时计算商品销量和库存；
- 把订单、支付和退款事件关联成订单状态。

消息系统负责保存和输送事件，流处理引擎或消费程序负责计算。消息系统本身不等于完整的流处理平台。

### 6.5 回放：重新读取已经处理过的消息

**回放（Replay）**是让消费者把读取位置移回过去，再处理一次历史事件。

常见用途：

- 新增一个推荐系统，需要用过去一个月的订单建立初始状态；
- 消费程序有 Bug，修复后需要重新计算；
- 搜索索引损坏，需要根据历史事件重建；
- 审计某个时间段内发生过什么。

回放要求消息在消费后仍被保留。任务队列通常把“处理完成”作为结束，而事件日志更强调“处理完成后历史仍然存在”，这是两类系统最根本的差异之一。

### 6.6 AMQP 路由：按规则把消息送到不同队列

AMQP 是一种消息协议。这里说的**复杂 AMQP 路由**，核心是 Broker 可以先接收消息，再根据路由规则决定它进入哪些队列。

例如一条订单消息可以：

- 按 `region=cn` 进入国内订单队列；
- 按 `type=refund` 进入退款队列；
- 同时复制给库存、通知和审计三个队列；
- 只把符合某种主题模式的消息交给特定消费者。

这种模型适合任务分发和企业系统集成。它关注“这条消息应该交给谁”，而分布式日志更关注“事件保存在哪个分片、消费者读到了哪里”。

### 6.7 TTL、优先级和短生命周期队列

**TTL（Time To Live）**表示消息或队列的有效期。例如验证码短信任务超过五分钟就没有继续发送的价值；过期后可以删除或进入死信队列。

**消息优先级**表示紧急任务可以比普通任务先处理。例如人工支付退款可以优先于普通对账任务。使用优先级意味着不再严格遵守先入先出。

**短生命周期队列**是随着连接、用户会话或临时任务创建，用完后自动删除的队列。例如：

- 为一次 RPC 请求创建临时响应队列；
- 为一个在线用户保存本次连接的通知；
- 为临时订阅者创建独立队列。

如果系统需要大量这种队列，重点是队列创建删除、路由和逐条确认的成本；如果系统需要长期保存同一条业务历史并反复读取，重点则是分片日志、保留时间和回放能力。

### 6.8 其他常见术语

- **Topic**：消息的逻辑分类，例如 `order-events`；
- **Queue**：等待某类消费者处理的消息集合；
- **Partition / 分片**：把一个大数据流拆到多个存储和处理通道，以提高并行度；
- **Consumer Group / 消费组**：多个消费者协作处理一份消息流，每条消息通常由组内一个成员负责；
- **积压（Backlog）**：已经进入消息系统、但尚未被消费者处理完的消息；
- **多租户**：多个团队或业务共享集群，同时在权限和资源上相互隔离；
- **存算分离**：处理客户端连接的服务节点与保存消息的存储节点分开扩容；
- **Broker**：接收、保存、路由或投递消息的服务端；
- **Brokerless**：没有统一 Broker，应用进程之间直接通信。

### 6.9 用业务问题快速判断

如果需求是“订单事件要保留三个月，未来新增系统还能读取历史，消费程序出错后可以重算”，核心是事件日志和回放。

如果需求是“把发送邮件、生成报表等任务按类型投递，失败后重试，紧急任务优先，过期任务不再执行”，核心是任务队列、路由、确认、TTL 和死信。

两种需求可能同时存在。大型系统常常分别选择合适的组件，而不是强迫一个产品承担所有通信模式。

## 7. 最小决策流程

1. 写出不能丢、允许重复、顺序范围、RPO 和 RTO；
2. 判断需要任务队列、可回放日志还是通信库；
3. 用峰值、消息大小、积压时间和业务 Key 分布建立容量模型；
4. 只保留满足硬约束的候选；
5. 对每个候选演练节点故障、网络分区、磁盘写满、消费者崩溃和扩容；
6. 用真实消息、真实并发和真实消费逻辑压测；
7. 最后比较运维复杂度和三年总成本。
