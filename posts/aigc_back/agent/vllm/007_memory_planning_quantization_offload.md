本节学习部署前最实用的工作之一：根据模型参数、精度和业务输入，估算模型是否能运行；如果不能，应该选择量化、卸载、分块还是多 GPU。

## 1. 不要只问“模型文件多大”

推理所需资源应拆成：

```text
峰值 VRAM
≈ GPU 常驻权重
+ 请求长期状态
+ 当前激活
+ 算子工作区
+ 运行时开销
+ 安全余量
```

对于文本模型，请求长期状态主要包括 KV Cache；对于 H3 类视频生成模型，则重点包括 conditioning、视频/音频 latent 和阶段输出。

CPU RAM 也需要单独估算：

```text
峰值 RAM
≈ CPU 常驻权重
+ 加载缓冲
+ Offload 权重
+ 解码后的输入
+ 输出帧和编码缓冲
+ 进程与系统开销
+ 安全余量
```

磁盘预算：

```text
磁盘
≈ 模型权重
+ 下载临时文件
+ 多版本和量化版本
+ 容器镜像
+ 输入输出文件
+ 日志
+ 安全余量
```

## 2. 第一步：估算权重

最基础公式：

```text
权重理论字节数 = 参数量 × 每参数位数 ÷ 8
```

假设模型为 30B：

| 精度 | 理论权重大小 |
| --- | ---: |
| FP32 | 120 GB |
| BF16/FP16 | 60 GB |
| INT8/FP8 | 30 GB |
| INT4 | 15 GB，加量化元数据 |

这是数量级估算，不是最终部署数字。模型还可能包含：

- 多个子模型；
- 未统计的 embedding、norm 等参数；
- 量化 scale、zero point；
- 未量化的敏感层；
- 权重对齐和格式开销。

## 3. 第二步：按组件估算

H3 不能只写一个总参数量，需要按组件拆开：

| 组件 | 磁盘精度 | GPU 运行精度 | 是否常驻 GPU |
| --- | --- | --- | --- |
| 文本/多模态编码器 | BF16/INT8 | BF16/INT8 | 可阶段卸载 |
| H3-Omni Transformer | BF16/FP8/INT8 | 依 kernel 而定 | 生成阶段主要常驻 |
| H3-VAE | BF16/FP16 | BF16/FP16 | 解码阶段使用 |
| 其他条件组件 | 视模型而定 | 视模型而定 | 按阶段 |

按组件统计有两个价值：

1. 找出最大的权重来源；
2. 判断哪些组件不需要同时驻留 GPU。

例如：

```text
编码器权重 10 GiB
Transformer 权重 40 GiB
VAE 权重 6 GiB
```

全部常驻至少约 56 GiB；如果三个阶段互斥并且框架支持卸载，理论上权重常驻峰值可能接近最大组件，而不是三者总和，但还必须加入 conditioning、latent、激活和传输缓冲。

## 4. 第三步：估算请求数据

### 4.1 文本模型

重点变量：

```text
并发请求数
每个请求的 token 数
层数
KV Head 数
head_dim
KV dtype
```

### 4.2 视频模型

重点变量：

```text
batch
帧数
输出高度、宽度
VAE 时间和空间压缩率
patch 大小
latent channels
激活 dtype
是否使用 CFG
Attention 实现
```

latent 自身可以粗略估算：

```text
latent bytes
= batch
× latent_frames
× latent_height
× latent_width
× latent_channels
× dtype bytes
```

但这只计算一份 latent，不能替代真实峰值测量，因为某一步可能同时存在输入 latent、输出、QKV、MLP 激活和工作区。

## 5. 第四步：保留安全余量

不能把理论数据填满全部显存。例如 24 GiB GPU 的方案若估算刚好为 23.9 GiB，通常是不可靠的。

需要为以下项目留余量：

- CUDA context；
- allocator 对齐与碎片；
- kernel workspace；
- 输入尺寸波动；
- 并发重叠；
- 框架版本差异；
- 监控和其他 GPU 进程。

安全余量没有统一比例。早期规划可以暂时保留约 10%～20%，但最终必须通过目标硬件和目标输入的峰值 profiling 确认。

## 6. 量化到底是什么

量化的核心目标是用更少的位表示权重或激活。

假设一组浮点权重：

```text
[-0.82, -0.31, 0.04, 0.47, 0.91]
```

量化会选择一个映射尺度，把它们近似表示成较低位整数：

```text
浮点权重 ≈ 整数值 × scale
```

一种简化表达：

```text
q = round(x / scale) + zero_point
x_approx = (q - zero_point) × scale
```

真实量化算法还涉及分组、异常值处理、校准、对称/非对称量化和特定硬件格式。

量化不是压缩包。权重在计算中必须由相应 kernel 读取，并以低精度计算或在计算路径中反量化。

## 7. Weight-only 与 W8A8

### 7.1 Weight-only

只量化权重，激活仍使用 BF16/FP16：

```text
W4A16：权重 INT4，激活 FP16/BF16
W8A16：权重 INT8，激活 FP16/BF16
```

优点：

- 显著减少权重占用和权重读取带宽；
- 通常比同时量化激活更容易保持质量。

局限：

- 激活和 Attention 工作区没有按权重比例缩小；
- 运行速度依赖低位 kernel；
- 可能有反量化成本。

### 7.2 Weight-and-activation

同时量化权重和激活：

```text
W8A8：权重 INT8，激活 INT8
FP8：权重和/或激活使用 FP8
```

可能进一步减少内存和提高吞吐，但更依赖硬件、校准和高质量 kernel。

## 8. PTQ 与 QAT

### 8.1 PTQ

Post-Training Quantization：模型训练完成后再量化。

```text
原始模型
  ↓ 使用校准数据或权重统计
量化模型
```

特点：成本较低、部署常用，但低位量化可能产生质量损失。

### 8.2 QAT

Quantization-Aware Training：训练或微调时模拟量化误差，让模型适应低精度。

```text
训练/微调时模拟量化
  ↓
模型学会适应低精度误差
```

通常有机会获得更好的低精度质量，但成本和工程复杂度更高。

## 9. 为什么量化后不一定更快

量化可以减少内存，但速度取决于完整执行路径：

```text
是否有目标 GPU 支持的低精度指令
是否有成熟 kernel
反量化成本
算子是否受显存带宽限制
是否出现 dtype 转换
小 batch 下 kernel 启动开销
量化格式是否被推理引擎原生支持
```

可能出现：

```text
显存下降，但速度基本不变
显存下降，但反而变慢
显存下降且吞吐提高
```

因此要分别测量：

- 权重大小；
- 峰值 VRAM；
- 加载时间；
- 单请求延迟；
- 并发吞吐；
- 输出质量。

## 10. 哪些内容不能简单量化

不同组件对精度敏感程度不同。常见策略是混合精度：

```text
大部分 Transformer 线性层：INT8/INT4/FP8
Norm、部分输出层：BF16/FP16
VAE：BF16/FP16，视实现和质量而定
敏感层或异常值通道：保留高精度
```

视频模型量化还要评估：

- 单帧细节；
- 多帧一致性；
- 运动稳定性；
- 人脸和文字质量；
- 音画同步；
- 长视频误差积累。

“生成成功”不代表质量可接受。

## 11. 剪枝是什么

剪枝尝试移除不重要的模型结构或参数。

### 11.1 非结构化剪枝

将部分权重变为零：

```text
原矩阵：大量非零值
剪枝后：部分元素为 0
```

如果硬件和 kernel 不支持高效稀疏计算，文件可能更容易压缩，但运行速度和显存不一定按零值比例下降。

### 11.2 结构化剪枝

移除完整的 head、通道、神经元、层或其他规则结构。

优点是更容易映射到稠密硬件；缺点是通常更容易影响模型能力，需要评测和可能的恢复训练。

### 11.3 量化与剪枝的区别

```text
量化：参数数量大体不变，每个参数用更少位表示
剪枝：减少实际参与模型的参数或结构
```

## 12. CPU Offload

CPU Offload 不改变模型本身，而是改变权重或张量放置位置：

```text
原方案：权重全部在 VRAM
Offload：部分权重/组件在 RAM，需要时搬到 VRAM
```

### 12.1 Offload 哪些东西

可能包括：

- 整个组件，如编码器或 VAE；
- Transformer 层或层组；
- 暂时不用的权重；
- 部分请求状态；
- 最终输出或中间结果。

### 12.2 性能为什么下降

GPU 显存内部带宽远高于 CPU 与 GPU 之间的 PCIe 传输带宽。若每一步都传输大量权重：

```text
传输时间 = 数据量 ÷ 有效 PCIe 带宽
```

假设每一步必须传输 20 GiB 权重，实际有效传输带宽为 20 GiB/s，仅传输理论上就约需 1 秒，还没有计算。

如果生成过程有许多步，权重反复搬运可能成为主要瓶颈。

### 12.3 异步预取

更好的实现会尝试：

```text
GPU 正在计算 Layer N
CPU 同时准备并传输 Layer N+1
```

即通信与计算重叠。但需要足够的显存缓冲和精细调度，实际效果取决于计算时间能否覆盖传输时间。

## 13. Disk Offload

当 RAM 也不够时，部分权重可放在 SSD，需要时读取：

```text
SSD → RAM → VRAM
```

它进一步降低内存门槛，但通常更慢，并且对 SSD 吞吐、随机读取和寿命有影响。它更适合“勉强跑通”或实验，不应在没有压测的情况下视为生产方案。

操作系统 Swap 也可能让进程暂时不崩溃，但模型推理会因为频繁换页变得极慢。Swap 不是大模型 RAM 的等价替代品。

## 14. VAE Tiling 和 Slicing

这两种技术主要降低 VAE 阶段的激活峰值，不直接减小 Transformer 权重。

### 14.1 Tiling

把大图像或视频空间区域切成小块分别解码：

```text
完整高分辨率 latent
  ↓ 切成多个空间 tile
逐块 VAE 解码
  ↓ 重叠区域融合
完整输出
```

优点：降低单次激活规模。

代价：

- 更多调用和计算；
- 重叠区域需要融合；
- 可能出现接缝或一致性问题。

### 14.2 Slicing

将 batch 或其他可分离维度分批处理：

```text
一次处理 N 个样本
→ 每次只解码其中一个或一部分
```

优点是降低峰值，代价是吞吐下降。

## 15. Attention 优化

Attention 中间结果可能很大。常见优化方向：

- FlashAttention / memory-efficient attention；
- 分块计算；
- 稀疏 Attention；
- sequence/context parallel；
- 降低分辨率、帧数或 batch；
- 使用更低精度激活。

这些方案作用点不同：

```text
权重量化：主要减少权重
KV Cache 低精度：主要减少文本请求缓存
FlashAttention：主要减少 Attention 中间读写和内存
VAE tiling：主要减少 VAE 激活峰值
CPU Offload：把 VRAM 压力转移到 RAM 和 PCIe
多 GPU 分片：把数据分布到多张 GPU
```

## 16. 优化方案选择顺序

遇到 OOM 时不要立刻随机组合所有优化。建议按以下顺序分析：

```text
1. 定位 OOM 阶段
2. 记录峰值和输入参数
3. 判断最大占用来自权重还是激活
4. 选择针对性的优化
5. 重新测量显存、延迟、吞吐和质量
```

### 权重放不下

优先考虑：

```text
量化
组件/层 Offload
多 GPU 权重分片
更小模型
```

### Attention 或 latent 激活过大

优先考虑：

```text
降低分辨率、帧数或 batch
内存高效 Attention
激活低精度
sequence/context parallel
```

### VAE 解码 OOM

优先考虑：

```text
先卸载 Transformer
VAE tiling
VAE slicing
分批或流式解码
```

### 并发导致 OOM

优先考虑：

```text
并发限制和队列
请求分桶
动态 batching
容量预留
多副本横向扩展
```

## 18. 没有大 GPU 时的选择

当前硬件不足以运行完整 H3 时，可以把学习目标拆成：

```text
结构分析：读取配置、权重索引、shape 和 dtype
容量设计：建立 BF16/INT8/INT4 预算
方案设计：单 GPU、多 GPU、offload 三套方案
小模型实验：验证量化、VAE tiling 和内存监控方法
VoxCPM 实战：在可用硬件上完成真实部署闭环
```

不要使用 VMware 的虚拟 3D 显卡作为 CUDA/ROCm 计算设备假设。CPU 路线可以验证功能，但不能代表生产 GPU 性能。
