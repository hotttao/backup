本节以 MiniMax H3 为例，建立多模态音视频生成模型的端到端心智模型。重点不是掌握 H3 尚未完全公开的所有内部细节，而是理解部署时会遇到哪些组件、数据和资源阶段。

<!-- more -->

## 1. 事实边界

根据 MiniMax 已公开的 H3 介绍，可以确认 H3：

- 能理解由文本、图像、视频和声音组成的多模态上下文；
- 能生成带原生双声道声音的视频；
- 最高支持 15 秒、2K 分辨率输出；
- 公开提到 Contextual Omni Representation、H3-VAE、H3-Omni Transformer 和 In-context Regeneration；
- 使用 H3-VAE 提高压缩效率，以缩短序列并降低训练、推理成本；
- 2K 生成使用基模进行 in-context regeneration，而不是一个传统的独立超分模块。

下面为了讲清部署流程，会将模型抽象成标准的多模态生成管线。具体组件名称、张量形状、调度算法和显存数据必须以实际版本的官方模型配置及源码为准。

## 2. H3 接收什么、输出什么

普通文本模型的接口相对简单：

```text
文本 → 文本
```

H3 的输入输出可以抽象为：

```text
输入：文本 + 可选图像 + 可选视频 + 可选音频
输出：视频帧 + 双声道音频
```

不同任务只是输入条件不同，例如：

```text
T2V：文本 → 视频
I2V：文本 + 首帧/参考图 → 视频
V2V：文本 + 参考视频 → 新视频
Ref2VA：文本 + 图像/视频/音频参考 → 音视频
```

对部署系统来说，不能只设计一个字符串参数。API 还需要处理：

- 多个输入文件；
- 文件格式和大小验证；
- 视频时长、帧率和分辨率；
- 音频采样率和声道；
- 输入与 prompt 中引用对象的对应关系；
- 生成分辨率、帧数、随机种子等参数。

## 3. 端到端流程

先建立一张总图：

```text
用户请求
├── 文本 prompt
├── 参考图像
├── 参考视频
└── 参考音频
       │
       ▼
输入检查与预处理
       │
       ▼
各模态编码 / 条件构造
       │
       ▼
Conditioning 条件表示
       │
       ├──────────────┐
       ▼              │
初始视频/音频 latent  │
       │              │
       ▼              │
H3-Omni Transformer ◄─┘
       │ 多步更新 latent
       ▼
最终音视频 latent
       │
       ▼
H3-VAE Decoder
       │
       ▼
视频帧 + 音频波形
       │
       ▼
后处理与 MP4 封装
```

下面逐段解释。

## 4. 第一步：输入检查和预处理

### 4.1 文本

文本需要经过规范化和编码：

```text
prompt 字符串
  ↓ 清理、模板化
token IDs
  ↓ embedding / 文本编码器
文本条件张量
```

### 4.2 图像

图像不能直接交给 Transformer，需要：

```text
图片文件
  ↓ 解码为像素
调整尺寸、色彩空间、数值范围
  ↓
图像张量
  ↓ 视觉编码或 VAE 编码
图像条件/latent
```

典型图像张量形状为：

```text
[batch, channels, height, width]
```

### 4.3 视频

视频文件其实是一个容器，可能同时包含视频轨和音频轨。预处理可能涉及：

```text
视频文件
  ↓ 解封装、解码
视频帧序列 + 音频
  ↓ 采样、缩放、裁剪、对齐
视频张量 + 音频张量
```

典型视频张量可表示为：

```text
[batch, channels, frames, height, width]
```

### 4.4 音频

音频预处理可能包含：

```text
音频文件
  ↓ 解码
波形
  ↓ 重采样、声道转换、归一化
音频张量
  ↓ 音频编码器
音频条件表示
```

注意：预处理通常主要消耗 CPU 和 RAM，也可能利用 GPU 加速解码或编码。大文件上传、视频解码和格式转换本身就可能成为部署瓶颈。

## 5. 第二步：条件表示 Conditioning

用户输入不是最终要生成的视频，而是对生成过程施加的条件：

```text
文本：描述生成目标
图像：约束人物、物体或画面
视频：约束动作、运镜或时序
音频：约束声音、节奏或其他音频信息
```

编码器把不同模态转换成模型可以读取的数值表示。可以先把 conditioning 理解为：

> 模型生成过程中持续参考的一组“任务说明和参考资料”。

例如：

```text
“参考视频 1 的运镜，让图像 2 中的人物唱歌，声音参考音频 3。”
```

系统必须保留：

- 各参考输入本身的表示；
- prompt 中各引用和输入之间的关系；
- 时间、空间和模态信息；
- 目标任务类型。

官方将相关方向称为 Contextual Omni Representation。部署时需要知道 conditioning 也占内存，但它和模型权重不是一回事：

```text
编码器权重：模型长期参数
conditioning：当前请求产生的中间状态
```

## 6. 第三步：为什么需要 latent

直接在原始视频像素上运行大型 Transformer 非常昂贵。

假设生成 5 秒、24 FPS、1920×1080 RGB 视频：

```text
帧数 = 5 × 24 = 120
像素通道值数量 = 120 × 1920 × 1080 × 3
                = 746,496,000
```

还未考虑音频、batch 和中间激活，就已经有约 7.46 亿个通道值。

因此生成模型通常先在压缩空间工作：

```text
原始音视频
  ↓ VAE Encoder
更小的 latent

生成过程主要修改 latent

最终 latent
  ↓ VAE Decoder
原始音视频
```

latent 不是普通压缩文件，也不是 JPEG/MP4。它是模型学习出来的一种连续数值表示，适合神经网络计算。

可以类比为：

```text
原始像素：最终成片的每一个细节
latent：较紧凑的“画面与运动工作底稿”
```

类比不代表 latent 中每个维度都有人类可解释的含义。

## 7. 第四步：初始 latent 从哪里来

不同生成任务的起点可能不同。

### 7.1 文生视频

通常从随机噪声或某种初始化状态开始：

```text
随机 latent
  + 文本等条件
  ↓ 多步生成
目标视频 latent
```

随机种子控制初始随机状态，因此相同模型、参数和输入在确定性条件满足时，可以产生可复现结果。

### 7.2 图生视频或视频编辑

参考图像或视频可能先编码为 latent，再按任务需要加入噪声或构造初始状态：

```text
参考图像/视频
  ↓ Encoder
参考 latent
  ↓ 加噪或任务变换
初始 latent
```

具体方式取决于 H3 的实际任务实现，不能在没有源码和配置证据时假定统一算法。

## 8. 第五步：H3-Omni Transformer 做什么

从部署视角，可先把 H3-Omni Transformer 理解为生成过程的主要计算核心：

```text
当前 latent
+ 时间步或生成阶段信息
+ 多模态 conditioning
        ↓
H3-Omni Transformer
        ↓
预测 latent 应如何更新
```

这个过程通常需要执行多次：

```text
latent_0（更像噪声）
  ↓ step 1
latent_1
  ↓ step 2
latent_2
  ↓ ...
latent_n（可解码的结果）
```

与自回归文本模型的区别：

```text
文本模型：通常循环生成下一个离散 token
视频生成：通常循环更新整块连续 latent
```

因此 H3 的一次迭代可能同时处理大量时空 token。分辨率、帧数和参考输入增加，会影响 latent、Attention 和中间激活规模。

## 9. 第六步：H3-VAE Decoder 做什么

Transformer 的最终输出仍处于 latent 空间，人无法直接观看或收听。VAE Decoder 将 latent 转换为音视频数据：

```text
最终 latent
  ↓ H3-VAE Decoder
视频帧张量 + 音频张量
```

VAE Decoder 不是普通格式转换工具，而是有自己模型权重和中间激活的神经网络组件。

因此部署时可能出现这样的峰值：

```text
Transformer 权重仍在 VRAM
+ 最终 latent
+ VAE 权重
+ 高分辨率解码激活
= VAE 解码阶段 OOM
```

一种常见优化思路是阶段性加载和卸载：

```text
生成阶段：Transformer 在 GPU，VAE 暂时在 CPU
解码阶段：卸载 Transformer，再把 VAE 放入 GPU
```

这样可以降低峰值显存，但会增加 CPU RAM 使用和 CPU-GPU 数据传输时间。实际能否这样做取决于框架实现。

## 10. 第七步：后处理和文件封装

神经网络输出通常仍是张量，需要进行：

```text
数值范围转换
颜色空间转换
帧率设置
音频采样率和声道处理
音视频时间同步
视频编码
封装为 MP4/WebM 等文件
```

这里通常会使用 FFmpeg 等工具。模型推理成功但最终文件损坏、无声、音画不同步，也属于部署故障，而不一定是模型本身失败。

## 11. 2K In-context Regeneration 的理解

MiniMax 官方说明 H3 的 2K 输出没有采用传统的独立超分模块，而是使用 H3 基模对低分辨率结果进行 in-context regeneration，并再次利用原有多模态上下文。

可建立如下简化认识：

```text
第一阶段结果 + 原始多模态条件
             ↓
再次由 H3 基模执行生成
             ↓
更高分辨率结果
```

这意味着高分辨率路径可能不是“低分辨率视频经过一个小型超分网络”这么简单，而是再次调用主要生成能力。因此需要关注：

- 第二阶段是否再次加载或复用主要权重；
- 是否产生新的高分辨率 latent；
- 总推理时间是否近似包含多个生成阶段；
- 峰值显存和累计计算量；
- 服务超时和任务队列设计。

具体步骤必须通过官方推理代码和 profiling 验证。

## 12. 组件、参数和请求数据的分类

| 内容 | 类型 | 生命周期 |
| --- | --- | --- |
| 多模态编码器权重 | 模型参数 | 常驻或按阶段加载 |
| H3-Omni Transformer 权重 | 模型参数 | 生成阶段使用 |
| H3-VAE 权重 | 模型参数 | 编码/解码阶段使用 |
| 文本、图像、视频、音频条件 | 请求中间数据 | 当前请求期间 |
| 初始和中间 latent | 请求中间数据 | 生成阶段 |
| Attention/算子工作区 | 临时数据 | 某一步计算期间 |
| 最终视频帧和音频张量 | 请求输出数据 | 后处理阶段 |
| MP4 文件 | 最终制品 | 保存至磁盘或对象存储 |

这张表是下一节分析 RAM/VRAM 生命周期的基础。

## 13. 没有大 GPU 时能学习什么

当前没有大型 GPU，仍然可以完成以下工作：

- 阅读模型配置和权重索引；
- 统计每个组件的权重文件大小；
- 使用 meta device 构造模型而不真正分配全部权重；
- 分析张量名称、shape、dtype 和理论内存；
- 研究预处理、后处理和任务 API；
- 用小型视频模型复现 latent、VAE 和多步生成概念；
- 设计 CPU offload 和多 GPU 切分方案；
- 使用理论数据编写容量规划表；
- 最后在 VoxCPM 上完成真实部署和测量。

“没有设备运行完整 H3”不等于不能学习 H3 的部署。FDE 也经常需要在获得客户硬件前，根据配置、权重和运行机制完成部署设计。
