# 方案六：DuckDB＋受限查询服务＋生成式看板

日期：2026-10-16。状态：研究候选，未部署、未测试。该方案复用 [方案五](05-trino-json-render-flint.md) 的展示与资产层，替换跨库计算和执行隔离方式。

## 1. 为什么独立列为一个方案

对于内部团队、有限并发、数据规模可控的场景，Trino 的独立 JVM 查询服务未必是唯一选择。DuckDB 官方已有同一条 SQL 关联 MySQL、PostgreSQL、SQLite 的示例和执行计划，因此可以比较“嵌入式 Worker”与“独立联邦查询服务”两条路径。[官方跨库示例](https://duckdb.org/2024/01/26/multi-database-support-in-duckdb)

新增路线是：**React＋json-render＋Flint → Python 应用 → 受限 DuckDB 查询 Worker → 多个业务源**。资产和业务定义仍保存在应用的 PostgreSQL；可先不部署 Trino、Superset、Cube、Marmot。

这减少了部分独立基础设施，但增加应用对任务调度、身份、资源限制、部门隔离和源库连接的管理责任。不能在没有数据规模与并发测量时认定总成本更低。

## 2. 已验证的事实与未验证项

| 项目 | 证据与状态 |
| --- | --- |
| 一条 SQL 跨不同数据库 JOIN | 官方有 MySQL＋Postgres＋SQLite 示例；本项目未实跑 |
| 读取线上 MySQL | 官方 MySQL 扩展支持查询时读取 |
| 只读连接 | MySQL attach 可指定 READ_ONLY，还应使用源库只读账号 |
| 查询下推 | 文档有 filter pushdown 设置；具体 SQL 的扫描量与远端行为待测 |
| 大表反复扫描 | 官方建议可考虑复制至 DuckDB；同步延迟与运维成本需计入 |
| 开箱即用部门隔离 | 本次未找到能直接满足本项目要求的完整链路，须由应用设计 |
| 自动可编辑看板 | 由方案五的应用层建设，DuckDB 不负责 |
| 跨源同一时点快照 | 不作承诺，不能从单库事务能力推导 |

连接行为、写入能力及下推设置依据：[MySQL 扩展](https://duckdb.org/docs/current/core_extensions/mysql)。

## 3. 执行方式

~~~mermaid
flowchart LR
  U[用户和部门身份] --> API[应用 API]
  API --> Q[校验后的 QuerySpec]
  Q --> S[按部门调度]
  S --> A[部门 A Worker]
  S --> B[部门 B Worker]
  A --> AV[源库 A 受限视图或副本]
  B --> BV[源库 B 受限视图或副本]
  A --> R[受权限约束的结果句柄]
  B --> R
  R --> UI[json-render 与图表适配器]
~~~

同一个部门 Worker 可以 attach 订单源、CRM 源等多个受限入口。图中的 A/B 是安全边界示意，不要求永远常驻两个进程；资源与回收策略按负载设计。

建议 Python 使用 DuckDB 客户端库嵌入 Worker，不通过命令行字符串执行。官方嵌入文档特别指出 CLI 有更多交互功能，推荐客户端库用于嵌入。[Embedding DuckDB](https://duckdb.org/docs/current/operations_manual/securing_duckdb/embedding_duckdb)

## 4. 部门隔离如何落地

### 首选：限制数据入口

源系统提供部门受限视图、独立数据库或独立账号可访问的数据范围。只读账号只能访问对应入口；Worker 只能连接允许的源。MySQL 没有因为使用只读账号就自动实现按部门过滤，必须实际限制表/视图权限或提供隔离副本。

例如 A Worker 的订单入口只返回 A 部门订单，CRM 入口只含其允许查看的客户和列。二者 JOIN 时还需明确以订单所属部门还是客户所属部门授权，不能让 Agent 自行选择边界。

### 数据入口无法限制时

需要服务端严格生成授权查询计划，再执行；不能让模型绕过 QuerySpec 访问原始表。AST 白名单、字段与关系校验是补充，应用需要对所有查询和函数通路建立完整控制。若短期无法建立可信边界，应使用既有具有成熟策略能力的数据服务，或保留 Trino。

仅在 SQL 末尾追加一个 department_id 条件不够：子查询、别名、跨源关联、聚合与函数都可能改变授权含义。

### 进程和结果隔离

不同安全域不共用带全域凭据的 DuckDB 实例；临时目录、secret、连接、结果缓存和错误输出都按安全域隔离。只建立两个 cursor 不应被视为安全边界。

这些是本方案必须实现并验证的约束，不是 DuckDB 自动提供的部门系统。

## 5. 不向模型开放通用 SQL 运行环境

DuckDB 官方把不可信 SQL 类比为需隔离执行的代码：SQL 可访问文件、网络、扩展与系统资源。仅禁止 INSERT/UPDATE 仍不能覆盖这些能力。[安全模型](https://duckdb.org/docs/current/operations_manual/securing_duckdb/overview)

拟采用：

- 管理员在部署时固定扩展与连接配置，模型不能 INSTALL、LOAD、ATTACH 或创建 secret。
- 查询由已发布指标/维度和受控模板生成；禁止任意外部路径、URL、宏、表函数和远端执行函数。
- 运行容器或进程限制可读文件、网络目的地、CPU、内存与临时磁盘。
- 后端设置执行期限、取消和必要时终止 Worker；排队与并发按部门配额。
- 只读附加与源库只读账号同时使用，服务端不泄露连接凭据。

不要盲目关闭所有外部访问后又期待 MySQL 扩展正常工作；初始化和运行权限应根据允许的数据源逐项验证，操作系统与网络隔离提供外层约束。

## 6. 哪些查询适合先试

适合：过滤后数据量小、数据源数量少、查询有明确时间范围、并发有限；也适合跨数据库与 CSV/Parquet 的分析任务。

需要谨慎测试：大事实表跨网络 JOIN、多面板频繁刷新、高基数明细、多个部门同时执行宽范围统计。可把热点结果汇总或复制至本地分析表，但这会引入数据落地、新鲜度和生命周期管理，不再是纯实时跨库查询。

比较引擎时用同一业务计划和相同来源数据，记录：源端扫描/返回行数、网络传输、峰值内存、临时盘、首个面板耗时、全看板耗时、取消与排队行为。LIMIT 只限制输出不能证明扫描成本低。

## 7. 与 Trino 版的关系

| 方面 | 方案五：Trino | 方案六：DuckDB Worker |
| --- | --- | --- |
| 查询部署 | 独立查询服务 | 嵌入应用管理的 Worker |
| 跨源 JOIN | connector/catalog | extension/attach |
| 身份与数据策略 | 可使用引擎访问策略 | 本方案依赖应用隔离及受限数据入口 |
| 查询调度 | 可复用查询服务能力 | 应用管理 Worker、排队与限额 |
| 展示和资产 | 自建 | 同一应用设计，可复用 |
| 适合的评估起点 | 共享查询、多源治理需求 | 有限规模、部署简化需求 |

这不是吞吐或性能排名。引擎替换也不意味着 SQL 可以完全不改：保留 QuerySpec，在各引擎适配器中处理函数、时区、类型和 NULL 语义。

本方案依据 current 嵌入式能力，未采用 preview 中 CONNECT/server 等新接口；不会把开发预览当已验证生产底座。

## 8. PoC 验收与退出条件

首先人工跨库查询，再加入 Agent，最后接看板：

1. 两个独立实例，覆盖 MySQL＋PostgreSQL；结果与人工基准一致。
2. 同样问题在 Trino 与 DuckDB 中比较，包含退款一对多、NULL、DECIMAL、时区和去重计数。
3. 两部门受限数据入口；恶意修改查询引用、目录、结果 ID、导出和缓存均不能越权。
4. 模拟请求超时、断线、源不可用和内存压力，能取消并回收 Worker。
5. 多面板刷新时测量真实源库压力，确认不会因每张图重复扫描破坏可接受负载。
6. 保存看板、重开、源更新后刷新与多轮编辑复用方案五的验收。

若源端隔离入口无法建设、查询压力不可控、应用调度代价过大或并发目标达不到，保留相同产品层与 QuerySpec，将执行适配器切回 Trino。

推荐定位：它是一个值得验证的较轻候选，暂不据此替代既定共享 BI 主线。不要先建设 DuckLake/Iceberg 等存储平台，除非实际查询测量已经说明需要数据汇聚。
