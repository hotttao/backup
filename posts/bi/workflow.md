# 优化后的 BI Agent 典型工作流

日期：2026-10-15。基于推荐的“Superset＋Trino＋官方 MCP＋轻量 Agent 适配”架构；本文件是设计建议和 PoC 验收计划，不代表已经实现或测试通过。

## 1. 用户看到的流程

1. 管理员接入数据并发布可用指标，配置部门访问范围。
2. 用户描述分析目标；口径不明确时，系统只澄清影响结果的歧义。
3. 系统生成图表预览，显示口径、时间、来源和刷新状态。
4. 用户将有用的图表一键加入已有仪表盘，或选择生成一份看板草稿。
5. 用户继续通过聊天或原生编辑器调整图表、布局和联动。
6. 重新打开看板时按当前访问者权限读取数据，保留可编辑性。

“加入看板”本身就是用户的保存操作，不再增加一轮重复确认。新增业务指标定义或跨部门授权，则由具有对应权限的人完成。

## 2. 一次准备与每次分析分开

### 管理员的一次准备

- 接入 MySQL、PostgreSQL 等数据源，验证跨源 JOIN；优先接只读副本或已有分析数据服务。
- 整理业务视图、主键、关联基数、时间字段、部门字段、枚举与单位。
- 发布少量业务指标与可用维度，给出明确中文描述和例子。
- 配置部门角色、数据集、行级限制、敏感列、资产读写范围。
- 为 Agent 发布经过验证的图表能力清单和工具清单。

连接器、图表插件和 API 版本变化时重新生成/校验能力清单，不把全部支持范围长期硬编码到提示词。

### 每次分析的状态流程（拟设计）

~~~mermaid
flowchart TD
  A[解析目标与登录身份] --> B[发现授权数据与业务定义]
  B --> C{关键口径是否明确}
  C -- 否 --> D[澄清歧义]
  D --> B
  C -- 是 --> E[拆分分析模块与查询计划]
  E --> F[校验权限 关联 粒度 成本]
  F --> G[执行查询并核对结果]
  G --> H{结果可用}
  H -- 可修复错误 --> E
  H -- 权限或数据缺失 --> I[说明缺口并结束本分支]
  H -- 是 --> J[选择图表 组织布局与交互]
  J --> K[渲染预览并验证]
  K --> L[用户一键保存或加入看板]
  L --> M[保存原生资产并读回核对]
  M --> N[多轮修改 版本追踪与反馈]
~~~

固定规则执行权限、类型、关联和配置校验；Agent 主要承担语义理解、模块拆解及解释。LangGraph 适合作为该状态流程的编排器；持久化只解决状态恢复，外部写入仍需幂等。[编排模式](https://docs.langchain.com/oss/python/langgraph/workflows-agents)、[持久化](https://docs.langchain.com/oss/python/langgraph/persistence)

## 3. 逐步输入、输出与检查

| 步骤 | 产物 | 关键检查 |
| --- | --- | --- |
| 0. 能力发现 | 当前 BI 支持的图表、字段角色和工具清单 | 以固定部署版本为准，限制首版支持范围 |
| 1. 身份绑定 | 当前用户、部门、可用角色和目录 | 由服务器读取，LLM 不可指定或扩大 |
| 2. 意图解析 | 分析目标、时间、指标、粒度、比较方式 | “收入”“最近一个月”等歧义明确 |
| 3. 业务定义匹配 | 指标 ID、版本、数据集和关联路径 | 优先复用已有口径，缺失则提出草稿 |
| 4. 模块拆解 | KPI、趋势、分组比较、明细等模块 | 每个模块回答一个清楚的问题 |
| 5. 查询规划 | 跨源 SQL/受控数据集查询及依赖 | 粒度、基数、权限、数据新鲜度可解释 |
| 6. 查询校验 | 可执行计划与受限预览 | 只读、限定表、时间范围、超时；不靠提示词保护 |
| 7. 结果核对 | 字段类型、行数、空值、合计和样本 | JOIN 重复放大、币种/时区、无数据与错误区分 |
| 8. 图表选择 | ChartSpec | 根据结果分布和字段类型选择，不只按用户句式猜 |
| 9. 布局与交互 | DashboardSpec、筛选映射和跳转映射 | 数据依赖、筛选联动、页面跳转分别表示 |
| 10. 预览 | 可查看的原生图表或嵌入预览 | 标题、单位、时间、截断、空态和联动 |
| 11. 保存 | BI 原生 chart/dashboard ID 与修订信息 | 身份、幂等、防覆盖、失败恢复、读回核对 |
| 12. 持续修改 | 差异更新与来源记录 | 保留人工编辑，指标变更可追踪 |

预览查询限制返回行数不等于限制源库扫描成本。跨源性能需要检查下推和实际扫描；大范围重复分析可以另建汇总/汇聚数据产品，而不是让 Agent 无限重试。

## 4. 图表能力清单

下表是首版建议，不是声称所有 BI 图表插件都已通过 Agent 验证。

| 类型 | 适合回答 | 必需信息 | 主要约束 |
| --- | --- | --- | --- |
| 指标卡 | 总额、数量、完成率 | 一个指标、统计时间、单位 | 单值口径明确；比率不能直接求和 |
| 折线图 | 趋势、周期变化 | 时间维度、粒度、指标 | 时间有序，缺失日期处理明确 |
| 柱状图 | 类别比较、Top N | 分类维度、指标、排序 | 高基数限制和“其他”规则明确 |
| 明细表 | 核对、定位具体对象 | 授权字段、分页、稳定排序 | 敏感列不可通过导出绕过 |
| 散点图（后续） | 两个数值的关系 | 同一对象粒度的两个指标 | 不把相关性解释为因果 |
| 漏斗图（后续） | 有序步骤转化 | 事件顺序、对象与时间窗口 | 不能仅把互不相关计数排成漏斗 |

先完成前四种的保存、编辑与联动，再扩大类型。饼图只在少量类别且确实构成整体时选用，不作为默认出图形式。

## 5. 两种图结构必须区分

**查询依赖图**：例如先确定 Top N 客户，再拉取这些客户的明细。无依赖的模块可以并行执行，数量受查询引擎并发限制。

**交互关系图**：例如点行业柱状图筛选明细、全局日期筛选作用于趋势和 KPI、点击订单打开明细页。这不是数据计算的执行顺序。

明细跳转传递结构化参数，不拼接任意可执行代码。能否使用原生跨图筛选、哪些类型能作为触发器，需要按 Superset 版本、插件和实际图表验证；不支持时采用显式筛选或受控跳转。

## 6. 一个具体案例

用户：“分析最近 90 天各客户行业的净销售额，展示趋势，点行业看本部门客户的订单明细。”

拟拆分：

- 净销售额 KPI：支付金额扣已确认退款；以既定业务口径为准。
- 日/周趋势：时间粒度根据记录量与展示宽度选择。
- 行业比较：订单源与 CRM 客户源关联。
- 明细表：订单、客户、金额等授权字段。
- 日期筛选：作用于所有适用模块。
- 行业联动：行业比较图筛选明细；是否同时筛选 KPI/趋势必须显式定义。

退款与订单若一对多，先按订单汇总退款再关联，避免金额被重复累加。客户行业应说明使用当前行业还是订单发生时行业。部门归属到底依据订单还是客户，应遵循授权规则，而非由模型临时选择。

跨源查询不提供统一全局快照的默认承诺；预览应记录查询时间与已知源延迟。重要对账采用一致的快照或汇聚口径。

## 7. 轻量配置示意

以下 YAML 是本项目拟设计的内部 DTO，不是 Superset、Trino 或 LangGraph 的原生配置，也不能直接调用产品 API。ID 和指标名均为示意。

~~~yaml
schema_version: 1
analysis:
  dataset_ref: orders_enriched_v1
  metric_refs:
    - id: net_revenue
      version: 1
  time:
    range: last_90_days
    timezone: Asia/Shanghai

dashboard:
  title: 行业净销售额分析
  charts:
    - key: revenue_trend
      query_ref: trend_query
      kind: line
      encoding:
        x: paid_date
        y: net_revenue
      layout: {x: 0, y: 0, w: 8, h: 4}
    - key: revenue_by_industry
      query_ref: industry_query
      kind: bar
      encoding:
        x: industry
        y: net_revenue
      layout: {x: 8, y: 0, w: 4, h: 4}
    - key: order_details
      query_ref: details_query
      kind: table
      layout: {x: 0, y: 4, w: 12, h: 5}
  filters:
    - key: time_range
      targets: [revenue_trend, revenue_by_industry, order_details]
  interactions:
    - from: revenue_by_industry
      action: filter
      field: industry
      targets: [order_details]

persistence:
  target_dashboard_ref: user_selected
  base_revision: 3
  operation_key: server_generated
~~~

用户与部门权限不写进这份模型生成的配置，而由服务端请求上下文附加。这里的 12 列网格是应用层抽象，适配器需转换成目标 BI 的布局格式。

## 8. 保存与多轮修改的实现边界

1. 预览不等于所有资产都已保存。用户点击保存后，创建或复用数据集、保存图表、更新看板布局与筛选，再读回校验。
2. 用操作 ID 和资产映射避免断线重试生成重复图表。若中途失败，保留可恢复草稿，或清理本次新建且未被其他资产引用的对象。
3. 不假定多个 REST/MCP 调用是原子事务。
4. 再次修改前读取 BI 原生资产与修订基线；若用户在原生编辑器改过布局，不用旧 DTO 整体覆盖。
5. 原生 BI 资产作为已保存状态的权威记录；内部 DTO 保存来源、版本和映射。跨端编辑应明确合并规则。
6. 切换部门或撤销权限后，历史聊天、预览、缓存、导出和看板刷新都重新检查访问权，不沿用旧结果扩大权限。
7. 无数据、权限拒绝、查询超时、源不可用分别显示；不生成虚构数值填充图表。

## 9. PoC 验收计划

以下均为待执行验收，不是本次已跑测试。第一轮用两个独立实例（MySQL＋PostgreSQL，或两个 MySQL）和两个部门账号。

| 验收点 | 通过条件 |
| --- | --- |
| 真跨源查询 | 单条查询同时使用两个源，结果与人工基准一致 |
| 业务正确性 | 含一对多退款、空客户、重复维度样本，金额不放大 |
| 中文与口径 | 同义问法命中同一指标；歧义会澄清 |
| 聊天出图 | KPI/趋势/比较/明细均能预览并给出来源 |
| 一键入看板 | 保存到指定已有看板，刷新浏览器后仍存在 |
| 后续编辑 | 原生编辑与聊天修改能共存，不覆盖无关更改 |
| 联动 | 行业与日期筛选作用范围符合定义 |
| 部门行隔离 | A 无法通过聊天、看板、直接链接或导出看到 B |
| 列与模型隔离 | 未授权字段不出现在发现结果、SQL结果和摘要中 |
| 缓存隔离 | B 不能命中包含 A 私有数据的结果 |
| 重试与恢复 | 保存中断后恢复不会重复创建或留下错误发布状态 |
| 数据刷新 | 源更新后按约定刷新策略出现新数据，时间可解释 |
| 性能 | 记录首响、查询耗时、P50/P95、扫描量、源库压力 |
| 版本兼容 | 固定版本工具清单与 DTO 映射一致 |
| 授权撤销 | 移除角色后历史资产及缓存不能继续被未授权读取 |

建议建立一组覆盖上述情形的 20～30 个代表问题作为首轮回归集合，数量是验证计划而非质量保证。不在缺少数据量与并发目标时预先承诺延迟指标。

## 10. 对原始四步工作流的调整

保留“能力定义—意图拆解—图表选择—组织看板”的主线，但在前面补身份、业务口径与跨源建模；选图前先取得并校验真实结果；组装阶段明确筛选与跳转；末尾增加原生资产保存、权限验收和多轮维护。

最先跑通的闭环是：**授权数据发现 → 一个跨源指标 → 正确图表 → 加入可编辑看板 → 两部门隔离 → 再次修改**。完成这个闭环后再扩展复杂 Agent 规划。
