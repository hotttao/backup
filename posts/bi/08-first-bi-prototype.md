# 从哪里开始：用一个最小原型理解 BI 并验证方案

日期：2026-10-16。本文收敛前面的调研，给出执行顺序；尚未部署或完成验收。

**先做方案二的缩减版：Superset＋单节点 Trino。先手工完成 BI，再接官方 MCP，最后接 Agent。**

第一轮只回答：两个数据库的数据，能否按正确口径做成可保存、可编辑、可刷新、按部门隔离的看板？暂时不用决定最终全部组件。

**现在从这里动手：**启动 Superset 和持久元数据库，接入一个测试 MySQL，手工做出净收入指标卡、日期趋势和日期筛选。保存看板、重新打开，再修改测试数据并刷新，确认金额正确。完成这一关，再加入 Trino 和第二个业务数据库。

执行顺序固定为：**手工 BI → 跨库关联 → 两部门隔离 → 固定 MCP 调用 → Agent 自然语言操作**。每关的通过标准见第 4 节；扩展与运维责任见第 5 节；遇到阻碍后的取舍见第 6 节。

## 1. 先理解六个对象

| 对象 | 用本次案例理解 | 谁负责 |
| --- | --- | --- |
| 数据源 | MySQL 的订单、退款；PostgreSQL 的客户行业 | 业务数据库 |
| 查询引擎 | 把两个数据库的数据放进同一条 SQL 中关联 | Trino |
| 数据集 | 一张整理好的分析表，例如“一行一订单，含行业、部门、净收入” | 人工 SQL＋Superset dataset |
| 指标与维度 | 指标是净收入之和；维度是日期、行业 | 数据集中的可信定义 |
| 图表与看板 | 柱状图表达行业差异；看板把指标卡、趋势、柱状图组织起来 | Superset |
| Agent | 将“按行业看净收入”转换成对已有数据集和图表工具的操作 | 最后加入的调用方 |

业务语义层保存“净收入怎么算、按什么粒度关联”等定义；首版用 SQL、指标和说明就能开始。Wren/Cube 能帮助管理和执行更复杂的语义，但不能代替看板编辑器。json-render/Flint 帮助构建展示，也不负责跨库计算和部门权限。

~~~mermaid
flowchart LR
  A[稍后加入：聊天 Agent] --> B[Superset：数据集 指标 图表 看板 权限]
  U[先手工使用原生 UI] --> B
  B --> C[Trino：跨源 SQL]
  C --> D[MySQL：订单 退款]
  C --> E[PostgreSQL：客户]
  B --> M[应用元数据库：保存图表 看板 用户 配置]
~~~

注意应用元数据库与业务数据源的区别：前者主要保存 BI 配置和资产，不是为了存放所有订单。前者丢失会丢看板定义，后者中断会影响查询和刷新。

## 2. 为什么从这个方案开始

当前最大的未知是 BI 的产品行为与数据正确性。使用现成编辑器，可以直接观察数据集、指标、图表、筛选、保存与刷新，再判断自建究竟要实现多少东西。Python 技术栈也便于你在确实需要时阅读或扩展后端。

Trino 则直接验证你已明确的跨物理数据库需求。官方 MySQL connector 支持与其他实例、其他系统关联；具体查询成本仍需自己测试。[官方说明](https://trino.io/docs/current/connector/mysql.html)

这延续 [方案二](02-superset-trino-agent.md)，只缩小首版范围。Metabase 仍是可行的成熟 BI 备选，但当前不同时搭两套 UI；Wren 新版留作语义能力的后续候选。

| 路线 | 功能扩展方式 | 运维负担主要来自 | 当前取舍 |
| --- | --- | --- | --- |
| Superset＋Trino | 先配置数据集与指标，再用 MCP/REST 补操作；必要时 Python/React 扩展 | 两个应用的配置、升级、身份，以及源库查询压力 | 首个原型 |
| Metabase＋Trino | 原生资产＋外部 API；深改核心要学习 Clojure | 仍有 BI、元数据库和查询引擎；授权与版本要核对 | UI 或操作适配确有阻碍时再对照 |
| Wren 新版＋自建 UI | 复用语义模块，产品体验自由设计 | 除查询外，还要维护编辑器、资产、身份、刷新链路 | 理解产品需求后再决定 |
| DuckDB＋自建应用 | 嵌入执行、自建查询与展示协议 | 进程较少，但排队、限额、隔离和大量产品代码由自己维护 | 有实测资源约束时再比较 |

这些是当前需求下的责任比较，不是性能排名。可扩展性要区分“增加配置”“编写适配代码”和“增加常驻服务”，不能只看项目是否开源或容器数量。

## 3. 固定一个小业务案例

只用测试数据。金额统一单位，退款归属订单日；本例净收入为实付金额减该订单已记录的退款，不覆盖真实财务确认规则。

MySQL 保存 orders、refunds；PostgreSQL 保存 customers。三张表均有 dept_id。订单 ID 在本例全局唯一，客户 ID 只在部门内唯一。

| 订单 | 部门 | 客户 ID | 订单日 | 实付 | 退款明细 | 净收入 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | A | 1 | 10-01 | 100 | 10、20，两笔 | 70 |
| 2 | A | 2 | 10-02 | 80 | 5 | 75 |
| 3 | B | 1 | 10-01 | 50 | 无 | 50 |
| 4 | B | 2 | 10-02 | 60 | 10 | 50 |

两个部门中，客户 1 的行业都是软件，客户 2 都是零售。正确答案固定为：

- 总实付 290，总退款 45，净收入 **245**。
- A 部门净收入 **145**，B 部门 **100**。
- 软件行业 **120**，零售行业 **125**。

这组数据故意包含两种常见错误：退款直接 JOIN 会重复累计订单实付；客户关联漏掉部门会产生重复匹配。先按订单汇总退款，再用正确键关联客户，得到“一行一订单”的数据集。

通过这个例子理解“粒度、关联基数、指标口径”，比先掌握某个语义层配置语法更有帮助。

## 4. 按顺序过四关

### 第一关：手工 BI，不接 Agent

先启动 Superset 和持久元数据库，只接 MySQL。用订单与退款做一张“一行一订单”的数据集，保留 dept_id、订单日和净收入。

亲手完成：一个净收入指标卡、一条按日趋势、一个日期筛选；加入看板，拖动位置、调整尺寸，保存后重新打开。

**通过标准：净收入等于 245；布局保存；修改一笔测试订单后，重新查询能反映变化。** 首轮关闭结果缓存或明确强制刷新，避免把缓存误判成 SQL 错误。

到这里应能解释：数据集不是图表、改布局不应改查询、保存看板不等于冻结数据。今天的第一个可交付目标就到这里。

### 第二关：加入 Trino，完成跨库关联

启动单节点 Trino，配置 MySQL 与 PostgreSQL 两个 catalog。先在 SQL 客户端执行关联，确认总量和行业分组；然后在 Superset 建 Trino 连接，将相同查询保存为虚拟数据集。

数据集保持一行一订单，包含 dept_id、订单日、industry、net_amount；指标定义为 SUM(net_amount)。增加行业柱状图，和指标卡、趋势放进同一个看板。

**通过标准：总额 245、软件 120、零售 125；同一日期范围下三张图能对账；客户行业更新后刷新能反映变化。**

只保存虚拟数据集即可开始，不需要先解决所有 connector 的持久视图能力。此时也不加独立 Wren/Cube 服务。

### 第三关：两个部门，共享计算服务

创建 A/B 两个普通 BI 用户。首版采用明确的部门受限 Trino 身份及各自的 BI connection，两个身份仍连接同一 Trino 服务；BI 端限制连接、数据集和资产访问。

Trino 必须配置可信认证与访问策略：每个身份只能读取本部门参与关联的数据，拒绝冒充其他身份。A/B 不能通过更改客户端用户名取得对方身份。其用户/表规则、行过滤等能力见 [访问控制文档](https://trino.io/docs/current/security/file-system-access-control.html)。

部门身份在服务端选定，不能让模型或筛选器选择。这个办法会增加连接和数据集配置，适合先用两个部门验证边界；后续再评估统一身份透传。

**通过标准：A 只能得到 145，B 只能得到 100；猜测对方图表/看板 ID、查询或导出均不能取得对方数据。** 测试用户不授予管理员、全库访问或任意 SQL 权限。只隐藏页面菜单不算通过。

这一步不需要完整的企业 SSO，但必须有实际权限边界。如果做不到，就停在测试数据阶段，先解决身份和查询权限。

### 第四关：确定性工具调用通过后，再接 LLM

先用固定参数调用官方 MCP，完成“已有数据集→图表预览→保存图表→加入指定看板”。首轮允许固定图表类型、布局和日期范围；不先做自动规划完整看板。

Superset MCP 是单独进程，能够查询和操作 BI 资产；它自身不等于聊天产品。[部署与认证文档](https://superset.apache.org/admin-docs/6.1.0/configuration/mcp-server/)

固定调用成功后，用一个小 Python 程序或现成 MCP 客户端接模型。只开放已授权数据集和已验证操作，业务说明只需明确一个指标、两个维度和三种图表。首版无需新增 Agent 框架、长时记忆或向量数据库。

让用户说三句话：

1. “看这个月的净收入趋势。”
2. “再按行业比较，加入这个看板。”
3. “把柱状图改成横向，保留其他图表。”

**通过标准：生成的是可继续编辑的原生资产；重开和刷新有效；手工调整的其他面板保留；A/B 身份经 MCP 仍正确；重试不重复加图。** 若原生工具不足，再补最小 REST 适配。

先用简单预览链接也能验证 AI 操作能力。产品中“聊天预览旁一键加入看板”的按钮，随后用薄聊天页补上；只有按钮真实完成保存、刷新和继续编辑，才算完整体验通过。

## 5. 运维到底复杂在哪里

首轮设计上的核心是 Superset Web、应用元数据库、Trino；自建测试源另加 MySQL 和 PostgreSQL，形成五个逻辑服务。后期 MCP 再增加一个进程，独立 Agent 服务按需要增加。初始化任务、官方 Compose 的开发辅助服务不应被误算成每源一套 BI。

部署时先固定前述研究的 Superset 6.1.0 基线，并记录 Trino、驱动、镜像和配置版本；不使用浮动 latest。使用该版本所需的配置与依赖，不以这里的逻辑服务数承诺某个官方模板可以直接删减。

| 操作 | 实际新增责任 |
| --- | --- |
| 新接一个数据库 | catalog、只读凭据、网络、字段映射和权限；通常不复制整套 BI |
| 新增一个指标或图表 | 数据集/指标配置、正确性核验、资产权限；通常不增加常驻服务 |
| 新增一个部门 | 身份、受限连接、数据集和资产授权；首版方案会增加配置维护 |
| 增加同时刷新的用户 | 测源库压力、查询时间、排队和资源；再决定缓存、Worker 或 Trino 扩容 |
| 升级 BI 或工具接口 | 备份元数据库与配置，回归三张图、保存操作和权限路径 |

BI 元数据库、配置及密钥的备份是一项责任；业务源数据备份是另一项。无状态 Web 可重建，不代表整个系统没有持久状态。

首轮保持单机测试、同步小查询。异步任务、报表定时发送、高可用和统一登录在需求出现后逐项增加。官方 Compose 用于尝试/开发，不能原样当成生产部署方案。[部署边界](https://superset.apache.org/admin-docs/installation/docker-compose/)

小数据通过后，只增加一次接近实际业务范围的查询测试：记录单图耗时、整个看板刷新耗时、源端扫描/负载、Trino 内存与失败恢复。先声明可接受目标，再判断结果；四条测试订单不能证明大表性能。

## 6. 何时继续，何时换方案

| 观察结果 | 下一步 |
| --- | --- |
| 原生编辑器可接受，工具适配工作明确 | 继续方案二，补薄聊天页 |
| 查询和权限通过，UI/保存操作是主要阻碍 | 保留同一 Trino、数据与验收案例，再替换为 Metabase 对照 |
| 简单指标尚可，复杂口径和关系持续重复实现 | 在相同案例上单独试 Wren 语义组件，再判断是否引入 |
| 跨源查询对源库造成不可接受压力 | 先测试副本、汇总或同步分析仓库；更换 Agent 不会解决它 |
| 产品必须高度定制，且已清楚现成 UI 的具体缺口 | 再进入方案五，逐项承接编辑、资产与权限责任 |
| 资源预算确实无法容纳查询服务 | 针对相同查询测试 DuckDB，并计入应用调度和隔离成本 |

每关只保留一个通过/失败记录、实际结果和阻塞点。当前下一步是**手工做出一个净收入看板并验证保存与刷新**，完成后再加入跨库查询；不再横向增加新项目。
