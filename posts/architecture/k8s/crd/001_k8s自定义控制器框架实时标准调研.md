# Kubernetes 自定义控制器框架与实时标准调研

## 1. 调研结论

如果问题是“现在实现 Kubernetes 自定义控制器，哪个框架算标准”，建议把“标准”拆成两层理解：

1. **Kubernetes 官方标准**：不是某一个控制器框架，而是 Kubernetes API 扩展和控制器模型本身，包括 CRD、声明式 API、控制循环、`spec/status` 分离、结构化 OpenAPI Schema、Conditions、Finalizer、API 版本演进、RBAC 和可观测性等约定。
2. **事实上的 Go 实现标准**：`sigs.k8s.io/controller-runtime`。它是 Kubernetes SIG 生态的控制器运行时库，被 Kubebuilder 和 Operator SDK 共同使用。
3. **项目脚手架标准**：Kubebuilder。它负责生成 API、Controller、RBAC、CRD、Webhook 和测试骨架，底层运行时仍是 controller-runtime。
4. **Operator 产品化工具链**：Operator SDK。Go 项目同样基于 Kubebuilder/controller-runtime，并额外提供 Ansible、Helm、bundle、Scorecard、OLM/OperatorHub 等能力。

因此，对于一个新的 Go 自定义控制器项目，推荐基线是：

> Kubernetes CRD/API 设计规范 + Kubebuilder 脚手架 + controller-runtime 运行时 + controller-gen/kustomize 生成与发布 + envtest 测试。

如果只是实现一个控制器，不需要 Operator 生命周期管理，直接使用 Kubebuilder 即可；如果要面向多个集群、需要打包发布、升级管理和 OperatorHub/OLM 集成，再考虑 Operator SDK。

## 2. 什么才是 Kubernetes 的“实时标准”

### 2.1 API 扩展标准

Kubernetes 官方推荐优先使用 CRD 扩展 API。CRD 由 API Server 托管，客户端可以像操作内置资源一样通过 `kubectl` 和 Kubernetes API 访问自定义资源。只有需要高度定制 REST 行为、特殊存储或复杂 API 语义时，才考虑 Aggregated API Server。

一个合格的 CRD 至少应关注：

- 使用 `apiextensions.k8s.io/v1`；
- 为每个版本提供结构化 OpenAPI v3 Schema；
- 明确 `served` 与 `storage` 版本；
- 将用户期望写入 `spec`，将控制器观察到的结果写入 `status`；
- 用 `status.conditions` 表达可观察状态，而不是只写一个布尔值；
- 对破坏性 API 变化设计多版本和 conversion webhook；
- 需要异步外部清理时使用带域名的 Finalizer；
- 通过 `+kubebuilder` markers、`controller-gen` 和 CI 保证生成文件与 API 类型一致。

Kubernetes 文档还明确说明，CRD 不是通用业务数据库。不要把大规模应用数据、终端用户数据或监控时序数据全部存进 Kubernetes API；CRD 更适合存储声明式配置和控制器需要管理的状态。

### 2.2 控制器标准

控制器的核心不是“监听事件后执行一次动作”，而是持续将实际状态收敛到期望状态：

```text
读取期望状态（spec）
        ↓
读取实际状态（集群资源和外部系统）
        ↓
计算差异
        ↓
执行幂等的变更
        ↓
更新 status/conditions
        ↓
等待事件或重新排队，再次 reconcile
```

控制器应遵循 level-based、幂等和可重试的设计。一次 Reconcile 可能因为缓存延迟、网络错误、资源版本冲突或外部系统暂时不可用而失败，因此不能依赖事件顺序，也不能把“只处理 Create/Update/Delete”当作业务模型。

## 3. 主流框架对比

| 方案 | 定位 | 底层/语言 | 适合场景 | 结论 |
|---|---|---|---|---|
| client-go | Kubernetes 低层客户端和 informer/workqueue 基础库 | Go | 需要完全控制缓存、队列、事件和同步机制 | 能力最底层，样板代码和治理成本高 |
| controller-runtime | 通用 Controller/Manager/Cache/Client/Reconciler 运行时 | Go | 新建 Go 控制器、Operator、Webhook | 当前 Go 生态事实标准，推荐作为核心运行时 |
| Kubebuilder | API/Controller 项目脚手架与开发工具 | Go | 从零创建规范化项目 | 推荐的项目入口；底层使用 controller-runtime |
| Operator SDK | Operator 开发、打包、测试和发布工具链 | Go/Ansible/Helm | 需要 Operator 生命周期和生态集成 | Go 项目与 Kubebuilder 兼容；功能更多但约束也更多 |
| Kopf | Pythonic Operator 框架 | Python | Python 团队、自动化脚本、中小型 Operator | 可用但不是 Kubernetes Go 控制器的主流标准 |
| Java Operator SDK | Java Operator 框架 | Java | Java 技术栈和企业集成 | 适合 Java 团队，不是跨语言唯一标准 |
| kube-rs | Rust Kubernetes 客户端和控制器生态 | Rust | Rust 性能/安全/部署需求 | 生态成熟度和团队门槛需要单独评估 |

这里容易混淆的一点是：**Kubebuilder 和 Operator SDK 不是 controller-runtime 的替代品**。官方资料显示，Operator SDK 的 Go 项目使用 Kubebuilder 风格，并且底层使用 controller-runtime；两者的 Reconciler、Manager、Client 和项目布局有较强共性。

## 4. Operator 发布与生命周期工具链

当一个 Controller 只服务于个人项目或内部系统时，Deployment、CRD、RBAC 加 Helm/Kustomize 通常已经足够。如果要把它作为可安装、可升级、可分发的 Operator 交付，就会接触 Bundle、OLM、OperatorHub 和 Scorecard。

### 4.1 Bundle：Operator 的标准安装包

Bundle 是 Operator 的标准化安装描述包，通常包含：

- Operator Deployment；
- CRD；
- RBAC 和 ServiceAccount；
- Operator 版本信息；
- 安装范围和依赖关系；
- 升级关系和其他元数据。

常见结构如下：

```text
bundle/
├── manifests/
│   ├── operator.clusterserviceversion.yaml
│   ├── myresources.example.com.yaml
│   └── myoperator.clusterserviceversion.yaml
└── metadata/
    └── annotations.yaml
```

Bundle 通常会被构建成一个容器镜像，例如 `registry.example.com/my-operator-bundle:v1.0.0`。它不是 Operator 的运行镜像，而是描述“如何安装 Operator”的安装包，可以类比为 Operator 的安装程序或发行包。

### 4.2 OLM：Operator Lifecycle Manager

OLM 是运行在 Kubernetes 集群中的 Operator 生命周期管理器，主要负责：

- 安装和卸载 Operator；
- 安装 Operator 所需的 CRD、权限和依赖；
- 管理 Operator Deployment；
- 按版本关系执行升级；
- 判断升级条件和依赖是否满足；
- 维护 Operator 的安装状态。

例如，发布 `MySQL Operator v1.1` 后，OLM 可以根据声明的版本关系执行：

```text
MySQL Operator v1.0
          ↓
       OLM 升级
          ↓
MySQL Operator v1.1
```

OLM 管理的是 **Operator 本身**，不是替代 Operator 管理 MySQL 集群的业务逻辑。MySQL Operator 仍然通过自己的 Reconcile 循环创建、升级和修复 MySQL 集群。

### 4.3 OperatorHub：Operator 目录和分发入口

OperatorHub 可以理解为 Operator 的应用目录或应用商店，主要用于：

- 发现可用 Operator；
- 查看功能、版本和支持信息；
- 查看安装方式和文档；
- 了解 Operator 的成熟度和能力范围。

OperatorHub 通常不负责在集群中运行 Operator。它和 OLM 的关系可以概括为：

```text
OperatorHub：发现和展示 Operator
        ↓
Catalog：保存可安装的 Operator 元数据
        ↓
OLM：从 Catalog 选择、安装和升级 Operator
        ↓
Operator：执行实际的业务控制逻辑
```

### 4.4 Scorecard：Operator 质量检查工具

Scorecard 是 Operator Framework 提供的质量检查工具，用于发现 Operator 是否符合常见最佳实践，例如：

- CRD 是否有描述和 Schema；
- RBAC 是否存在明显的过度授权；
- Deployment 是否配置健康检查；
- 是否设置资源限制；
- 是否正确使用 OwnerReference；
- 是否支持升级和基本的安装测试；
- 自定义资源创建、更新和删除是否能够正常工作。

Scorecard 不是运行时组件，也不负责安装或升级 Operator。它更像是 Operator 发布前的静态检查和集成验证工具，可以作为 CI 的质量门禁。

### 4.5 四者的完整关系

以一个数据库 Operator 为例：

```text
Kubebuilder/Operator SDK 编写 Controller
                ↓
        Operator SDK 构建 Bundle
                ↓
       Scorecard 检查发布质量
                ↓
      Bundle 加入 Catalog/OperatorHub
                ↓
          OLM 安装到集群
                ↓
       Operator 管理数据库集群
```

可以用一句话区分它们：

| 组件 | 解决的问题 |
|---|---|
| Bundle | 如何把 Operator、CRD 和权限打成标准安装包 |
| OLM | 如何在集群中安装、升级和卸载 Operator |
| OperatorHub | 用户如何发现和选择 Operator |
| Scorecard | Operator 发布前是否符合质量和最佳实践 |

### 4.6 是否需要完整引入这套工具链

个人项目或企业内部的单一控制器，建议先使用：

```text
Kubebuilder
+ controller-runtime
+ CRD/RBAC
+ Helm 或 Kustomize
+ envtest
```

只有在以下场景才建议引入 Bundle、OLM 和 OperatorHub：

- Operator 需要交付给多个团队或多个集群；
- 需要标准化的安装、升级和回滚；
- 存在多个 Operator 及其依赖关系；
- 需要发布到公共或企业内部 Operator 目录；
- 需要通过 Scorecard 等工具建立发布质量门禁。

### 4.7 Operator SDK 初始化后的 Go 项目结构

使用当前 Go 插件初始化项目，例如：

```bash
operator-sdk init --plugins go/v4 \
  --domain example.com \
  --repo github.com/example/my-operator

operator-sdk create api \
  --group cache \
  --version v1alpha1 \
  --kind Memcached \
  --resource \
  --controller
```

完成初始化和 API/Controller 脚手架生成后，常见结构如下。不同 Operator SDK、Kubebuilder 插件版本可能会有少量差异；应以当前项目的 `PROJECT`、`Makefile` 和 CLI 输出为准。

```text
my-operator/
├── api/
│   └── v1alpha1/
│       ├── groupversion_info.go       # API Group/Version 注册
│       ├── memcached_types.go         # Spec、Status 和 CR 类型定义
│       └── zz_generated.deepcopy.go   # 自动生成的 DeepCopy 代码
├── controllers/
│   ├── memcached_controller.go         # Reconciler 和 Watch 配置
│   └── suite_test.go                   # envtest 测试入口（通常由脚手架生成）
├── config/
│   ├── crd/
│   │   ├── bases/                      # 生成的 CRD YAML
│   │   └── kustomization.yaml
│   ├── rbac/                           # Controller 所需 RBAC
│   ├── samples/                        # 示例 Custom Resource
│   ├── manager/                        # Operator Deployment
│   ├── default/                        # 默认 Kustomize 入口
│   ├── manifests/                      # Bundle/OLM 清单生成入口
│   ├── scorecard/                      # Scorecard 配置
│   ├── prometheus/                     # metrics/ServiceMonitor 配置
│   ├── webhook/                        # Webhook 配置（启用后出现）
│   └── certmanager/                    # Webhook 证书配置（启用后出现）
├── test/                               # 可选的集成测试和 e2e 测试
├── hack/                               # 许可证头等开发辅助文件
├── bin/                                # kustomize、controller-gen 等工具
├── Dockerfile                          # Operator 运行镜像
├── Makefile                            # generate、manifests、test、deploy 等命令
├── PROJECT                             # Operator SDK/Kubebuilder 项目元数据
├── go.mod                              # Go 模块及 controller-runtime 依赖
├── go.sum                              # 依赖校验和
├── main.go 或 cmd/main.go              # 创建并启动 Manager
├── bundle.Dockerfile                   # Bundle 镜像构建文件
└── bundle/                             # 执行 make bundle 后生成/维护的 OLM 包
    ├── manifests/
    ├── metadata/
    └── tests/
```

#### 目录之间的关系

```text
api/v1alpha1/*_types.go
        │  controller-gen
        ├──────────────────→ config/crd/bases/*.yaml
        └──────────────────→ zz_generated.deepcopy.go

controllers/*_controller.go
        │  controller-runtime
        └──────────────────→ 监听 CR 并执行 Reconcile

config/rbac/ + config/manager/ + config/crd/
        │  kustomize
        └──────────────────→ 集群安装清单

config/manifests/ + PROJECT
        │  make bundle / operator-sdk generate bundle
        └──────────────────→ bundle/ → Bundle Image → OLM
```

#### 重点文件说明

- `api/<version>/*_types.go` 是 API 的源代码。修改 `Spec`、`Status` 或校验 marker 后，需要重新执行 `make generate` 和 `make manifests`。
- `controllers/*_controller.go` 是业务控制逻辑。`Reconcile()` 从 API Server/Cache 读取对象，创建或更新子资源，并写回 Status。
- `config/crd/bases/`、`config/rbac/` 等通常是生成或拼装后的 YAML，不应把它们当作唯一事实来源；API 类型和 marker 才是 CRD 的主要源代码。
- `config/samples/` 只是示例 CR，不是测试数据存储，也不代表所有字段都是必填项。
- `Makefile` 将代码生成、镜像构建、测试、部署和 Bundle 构建串起来。常见目标包括 `make generate`、`make manifests`、`make test`、`make docker-build`、`make deploy` 和 `make bundle`。
- `PROJECT` 保存项目版本、插件、API Group/Version/Kind 等元数据，Operator SDK 会使用它判断项目布局和生成行为。
- `bundle/`、`bundle.Dockerfile` 只有在准备 OLM/Bundle 交付时才重要；如果直接通过 Deployment 或 Kustomize 部署，可以暂时不关注。

#### Go 项目和 Ansible/Helm 项目的差异

上面的结构针对 `go/v4` 插件。使用其他插件时，核心目录会变化：

| 项目类型 | 主要业务目录 | 核心配置 |
|---|---|---|
| Go Operator | `api/`、`controllers/` | Go 类型和 Reconcile 逻辑 |
| Ansible Operator | `playbooks/`、`roles/` | `watches.yaml` 和 Ansible Playbook |
| Helm Operator | `helm-charts/` | `watches.yaml` 和 Helm Chart |

三种项目仍然可以共享 `config/`、`Dockerfile`、`Makefile`、`PROJECT` 等基础结构，但业务逻辑的编写方式不同。

## 5. 推荐的技术基线

### 5.1 新项目默认方案

```text
Go
└── Kubebuilder
    ├── controller-runtime
    ├── controller-gen
    ├── kustomize
    ├── envtest
    └── Prometheus/structured logging
```

推荐的项目结构通常包括：

```text
api/<version>/              # CR 类型、Spec、Status、Conditions
controllers/                # Reconciler 和 watch 配置（Operator SDK Go 默认布局）
config/crd/                 # 生成的 CRD
config/rbac/                # 生成的 RBAC
config/samples/             # 示例 CR
config/manager/             # 控制器 Deployment
webhooks/                   # 可选的 defaulting/validation/conversion webhook
test/                       # envtest、集成测试和 e2e 测试
```

### 5.2 版本策略

controller-runtime 的版本不是独立随意升级的。它按照 Kubernetes minor 版本演进，兼容关系应以项目 `go.mod` 和上游兼容矩阵为准。调研时上游仓库给出的关系是：controller-runtime v0.24 对应 Kubernetes `k8s.io/*` v0.36，v0.23 对应 v0.35，后续主分支继续推进到更高版本。

实际项目不要只写“使用最新版”，而应建立以下约束：

1. 先确定生产集群的 Kubernetes minor 版本范围；
2. 选择与其兼容的 controller-runtime minor 版本；
3. 使用同一条兼容线的 `k8s.io/api`、`client-go`、`apimachinery` 和 `apiextensions-apiserver`；
4. 在 CI 中测试最低支持版本和目标版本；
5. controller-runtime 的 patch 版本可按发布说明升级，minor 升级必须阅读 breaking changes；
6. 不要让 Kubebuilder CLI、controller-gen、controller-runtime 和 Go toolchain 跨越未经验证的版本组合。

截至本文调研时，上游 controller-runtime 主分支的 `go.mod` 已指向 Kubernetes `v0.37.x` 依赖，并要求 Go 1.26；这代表主分支开发状态，不等于所有生产集群都应该直接跟随主分支。生产项目仍应以已发布版本和兼容矩阵为准。

## 6. Reconcile 实现规范

建议每次 Reconcile 采用如下顺序：

1. `Get` 主资源；如果是 NotFound，直接返回；
2. 处理删除流程：检查 `deletionTimestamp`，执行外部清理，清理完成后移除 Finalizer；
3. 校验输入和依赖资源；
4. 计算目标子资源，使用 OwnerReference、Labels 和稳定命名管理归属；
5. 创建或 Patch 子资源，尽量使用声明式 Apply 或精确 Patch，避免覆盖用户管理的字段；
6. 通过条件集合更新 `status.conditions`，记录 `observedGeneration`；
7. 对临时错误返回 error 触发退避重试，对明确的定时检查使用 `RequeueAfter`；
8. 记录结构化日志、事件和指标，确保可以从控制器日志定位一次调谐。

典型状态字段可以包含：

```go
type ExampleStatus struct {
    Conditions []metav1.Condition `json:"conditions,omitempty"`
    ObservedGeneration int64 `json:"observedGeneration,omitempty"`
}
```

状态条件建议使用 Kubernetes 通用的 `metav1.Condition`，至少维护 `Type`、`Status`、`Reason`、`Message`、`LastTransitionTime` 和 `ObservedGeneration`。不要在每次 reconcile 都无条件写 status，否则可能制造额外事件和调谐循环。

## 7. 测试和交付标准

一个可以进入生产评审的控制器，建议至少覆盖以下测试：

- API 类型和 CRD Schema 生成检查；
- Reconcile 的 happy path；
- 子资源不存在、配置漂移和重复执行；
- 主资源删除和 Finalizer 清理；
- 依赖资源不存在或权限不足；
- API Server 冲突、超时和外部系统失败后的重试；
- Status Conditions 和 `observedGeneration` 的正确性；
- 多 namespace/cluster scope 行为；
- webhook 的默认值和校验；
- RBAC 最小权限验证；
- 使用 controller-runtime envtest 的集成测试；
- 真实 Kubernetes 集群中的 e2e 测试。

Operator SDK 官方也推荐使用 controller-runtime 的 envtest 进行控制器测试。它启动 API Server 和 etcd 相关测试环境，不要求每次单元测试都依赖完整 Kubernetes 集群，适合放入 CI。

发布时至少需要准备：

- CRD、RBAC、Controller Deployment；
- 镜像的多架构构建和不可变版本标签；
- 安装/升级/回滚说明；
- 支持的 Kubernetes 版本范围；
- metrics、health probe、leader election 和 graceful shutdown；
- 资源清理策略和 Finalizer 风险说明；
- 变更日志以及 CRD 版本迁移方案。

## 8. 结合本项目的建议

如果后续目标是为个人项目或企业内部系统实现一个自定义控制器，建议采用以下路线：

### 阶段一：先实现标准控制器

- Go + Kubebuilder；
- 一个稳定的 `v1alpha1` 或 `v1beta1` API；
- `spec/status` 分离；
- 一个主 Reconciler；
- OwnerReference 管理子资源；
- Conditions、Finalizer、RBAC 和 envtest 一起完成。

### 阶段二：再补充生产能力

- webhook 默认值和校验；
- 多版本 conversion；
- 指标、事件、Tracing 和告警；
- 失败重试、限速、并发度和缓存范围调优；
- e2e、升级和灾难恢复测试。

### 阶段三：有明确需求时再引入 Operator SDK

只有在需要 Operator bundle、OLM、OperatorHub、Scorecard，或者团队已经有 Ansible/Helm Operator 流程时，才建议把 Operator SDK 作为主要 CLI 和发布工具。对于单一 Go 控制器，Operator SDK 带来的额外能力不一定抵消工具链复杂度。

## 9. 最终判断

“Kubernetes 自定义控制器的实时标准”可以这样表述：

> 设计上遵循 Kubernetes API/CRD 与声明式控制器规范；Go 实现采用 controller-runtime；项目生成和 API 生命周期采用 Kubebuilder；需要 Operator 生态交付时再采用 Operator SDK。

这比简单回答“用 Kubebuilder”更准确：Kubebuilder 是脚手架，controller-runtime 是运行时，Kubernetes API 约定才是控制器真正需要遵守的标准。
