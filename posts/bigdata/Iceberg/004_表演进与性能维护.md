# Iceberg 表演进与性能维护

> 本文解释为什么 Iceberg 的 Schema、Partition Spec 和 Sort Order 可以演进，以及为什么支持演进和事务并不等于表可以不维护。
>
> 表演进改变“以后怎样解释或写入数据”；维护任务改变“现有文件和元数据怎样组织”。两者要分开理解。

## 一、先看结论

| 能力 | 是否通常重写历史 Data Files | 解决的问题 |
|---|---:|---|
| Schema Evolution | 否 | 列的增加、删除、重命名、类型提升、重排 |
| Partition Evolution | 否 | 新数据采用新的分区布局 |
| Sort Order Evolution | 否 | 新数据采用新的排序/聚簇方式 |
| Rewrite Data Files | 是 | 合并小文件、应用新布局、清理 Delete Files |
| Rewrite Manifests | 否，不改业务数据 | 整理 manifest，提高元数据剪枝效率 |
| Expire Snapshots | 可能删除不再引用的数据文件 | 控制历史长度和元数据规模 |
| Remove Orphan Files | 删除任何 Snapshot 都不引用的文件 | 清理失败写入或异常遗留文件 |

可以把一张长期运行的 Iceberg 表看成两个循环：

```text
在线写入循环
写数据 → 提交 Snapshot → 对 Reader 可见

后台维护循环
分析文件分布 → compact / rewrite manifests
→ expire snapshots → remove orphan files → 监控
```

## 二、Schema Evolution 为什么不需要重写文件

Iceberg 通过 field id 建立逻辑列与物理文件字段之间的稳定映射：

```text
Schema v1
1: id
2: name
3: amount decimal(10, 2)

Schema v2
1: id
2: customer_name        # rename，ID 仍为 2
3: amount decimal(18, 2)# 安全类型提升
4: channel              # 新字段
```

旧文件没有 `channel`，Reader 按新 Schema 读取时将它解释为 null；旧文件中的 `name` 仍通过 ID=2 映射到 `customer_name`。

### 2.1 常见安全变更

- 增加列；
- 删除列；
- 重命名列；
- 调整列顺序；
- 部分允许的类型提升；
- 对嵌套 struct 字段做同类演进。

删除列通常只是从当前 Schema 移除字段，并不会立刻从旧 Parquet 文件擦除数据。因此它不是安全的数据销毁手段；如果有合规删除要求，需要重写相关文件并过期所有仍引用旧文件的 snapshots。

### 2.2 为什么不能随意复用 ID

```text
删除 ID=2 的 email
后来新增一个同名 email
```

新列必须使用新 ID。否则 Reader 可能把旧文件中已删除字段的值误认为新字段值。Iceberg 的正确性来自 ID，而不是“列名看起来一样”。

### 2.3 类型提升也有边界

类型变更必须保证旧值能够被新类型无歧义地解释。不能把任意 string 直接元数据修改成 bigint，也不能随意降低 decimal 精度。对于不兼容变更，应新增列、显式转换并回填，再逐步迁移读取逻辑。

## 三、Partition Evolution 改变什么

假设订单表最初每天数据不多，使用月分区：

```text
Spec 0: months(created_at)
```

数据增长后，查询主要按天访问，可以更新为：

```text
Spec 1: days(created_at)
```

变更之后：

- 旧文件仍带 `spec_id=0`，不移动、不重写；
- 新文件使用 `spec_id=1`；
- Planner 针对两套规则分别转换查询谓词；
- 用户仍过滤 `created_at`，SQL 不依赖物理分区列。

这让分区规则成为可演进的优化策略，而不是写进业务 SQL 的永久 API。

### 3.1 怎样选择分区粒度

分区过粗：

- 单分区文件很多；
- 时间范围查询仍需扫描大量文件；
- 并发写容易集中在热点分区。

分区过细：

- 分区值和 manifests 更碎；
- 每个分区数据量小，容易产生小文件；
- writer fan-out、内存和文件句柄压力上升。

目标不是“分区越细越快”，而是让主要谓词能排除大量文件，同时每个分区仍能形成大小合理的数据文件。

### 3.2 Bucket 数为什么不能只看并行度

`bucket(64, user_id)` 表示稳定哈希映射到 64 个值，它影响长期数据布局。计算引擎当前有多少 Task 是运行时资源问题，不能简单等同于 bucket 数。Bucket 太少会导致每桶过大，太多会放大小文件和 Writer 数量。

## 四、Sort Order Evolution 改变什么

Partition 负责粗粒度分组，Sort Order 决定新写文件内部或文件之间的数据聚簇倾向。

例如表按天分区，同时按 `user_id, event_time` 排序：

```text
day=2026-09-01
    File A: user_id 1 ~ 1000
    File B: user_id 1001 ~ 2000
```

查询 `user_id = 42` 时，即使 day 分区内有许多文件，Manifest 的 lower/upper bounds 仍可排除大部分文件。

更新 sort order 只影响后续写入。若历史文件随机分布，需要 rewrite data files 才能让旧数据获得新聚簇效果。

排序也有成本：Writer 可能需要 Shuffle 或本地排序；高频流写中严格全局排序通常不现实。应在写入成本、压缩率、查询剪枝和并发度之间权衡。

## 五、小文件是怎样产生的

### 5.1 分布式 Task 各自写文件

多个 Spark Task 或 Flink subtask 不会共同追加同一个 Parquet 文件。并行度过高、单批数据太少时，每个 Task 都可能产出小文件。

### 5.2 数据同时落入许多分区

一个 Task 若写入多个 partition，可能为每个 partition 维护独立 Writer，进一步切碎输出。

### 5.3 流式 checkpoint 太频繁

每个 checkpoint 都提交少量数据，长期运行后会积累许多小 Data Files、manifests 和 snapshots。

### 5.4 Update/Delete 产生碎片

Copy-on-Write 会生成替代文件；Merge-on-Read 会积累 Delete Files。两者都可能让文件布局偏离初始目标。

文件目标大小只是 Writer 的目标，不是保证。一个 Task 在某个 partition 只有 5 MB 数据时，不会凭空写成 512 MB 文件。

## 六、Rewrite Data Files 做什么

最常见的是 bin-pack compaction：

```text
10 MB + 20 MB + 35 MB + 50 MB 小文件
                ↓ rewrite
       一个或少数目标大小文件
```

更高级的 rewrite 可以按当前 sort order 或空间填充曲线重新组织数据，使相关值靠近，从而提升列统计剪枝效果。

执行流程通常是：

```text
选择候选 Data Files
        ↓
记录基线 Snapshot 和候选文件集合
        ↓
读取并重新组织 records，同时应用适用 Delete Files
        ↓
写出新 Data Files
        ↓
验证旧文件仍然有效
        ↓
原子提交：删除旧文件引用，增加新文件引用
```

Compaction 与在线 Writer 可以并行，但更容易遇到冲突，因为它要替换现有文件。任务应限制每批候选范围、配置合理重试，并避免多个 compaction 作业重写同一组文件。

---

## 七、Rewrite Manifests 做什么

持续 append 会产生许多 manifests。如果每个 manifest 很小，或文件条目没有按当前 partition spec 聚集，Manifest List 的一级剪枝效果会下降。

Rewrite Manifests 重新组织文件条目：

```text
许多零碎 manifests
M1: day1, day8
M2: day2, day9
M3: day1, day7
        ↓ rewrite manifests
更少、按分区范围组织的 manifests
N1: day1 ~ day2
N2: day7 ~ day9
```

它重写的是元数据文件，不是 Parquet 业务数据，因此与 Data File compaction 的成本和目的不同。

诊断时也要区分：

- Data Files 太小 → rewrite data files；
- Manifest Files 太多或布局差 → rewrite manifests；
- Snapshots 太多 → expire snapshots。

## 八、Expire Snapshots 做什么

每次提交都会产生 Snapshot。只要旧 Snapshot 仍被保留，它引用的旧 Data Files 就不能删除，因为 time travel 或 rollback 仍可能读取它们。

```text
Snapshot 100 → A, B
Snapshot 101 → A, C   # B 被替换
Snapshot 102 → A, D   # C 被替换

只保留 Snapshot 102 后
B、C 若不再被 branch/tag 或其他 Snapshot 引用，才可删除
```

过期快照会带来两个不可逆结果：

- 不能再 time travel 到该 Snapshot；
- 仅由已过期 snapshots 引用的数据和元数据文件可能被删除。

因此保留策略必须同时考虑：

- 业务需要的回溯窗口；
- 流式 Reader 可能落后的最大时间；
- branch/tag 的保留策略；
- 审计、合规和灾难恢复要求；
- 存储成本与元数据规模。

Snapshot 历史不是对象存储级备份。错误配置 expiration、误删 Catalog 或跨区域灾难仍需独立备份与恢复方案。

## 九、Remove Orphan Files 为什么危险

Orphan file 是不被任何有效表元数据引用的文件，常见来源：

- Task 写文件后，Job 在提交前失败；
- 提交状态未知，客户端重复或中止；
- 手工操作或旧工具遗留文件；
- 元数据清理不完整。

孤儿清理通常按“文件修改时间早于某阈值”寻找候选。如果阈值太短，可能删除：

- 正在运行但尚未提交的慢作业文件；
- 长 checkpoint 流任务产生的文件；
- 暂时无法从 Catalog 观察到、但即将提交的文件。

所以不要把 orphan cleanup 当作实时垃圾回收。应使用明显长于最大写入和提交时长的安全窗口，并先 dry run 或审计候选文件。

## 十、Branch、Tag 与 WAP

Iceberg Snapshot 可以通过 refs 暴露为 branch 或 tag：

```text
main ───── S100 ───── S101 ───── S103
              \
audit          └───── S102

tag: month_end_2026_08 → S100
```

- Branch 是可继续提交的命名引用；
- Tag 通常用于固定某个 Snapshot；
- 每个 ref 可以有独立保留策略；
- refs 引用的 Snapshot 会影响 expiration 能否删除历史文件。

Write-Audit-Publish（WAP）可以先把写入提交到审计分支，在完成质量检查后再发布到主分支。它解决的是数据上线流程，不自动替代测试、权限、血缘或业务审批系统。

## 十一、一套可执行的维护策略

不同表没有统一周期，但可以从指标驱动出发：

| 观察指标 | 可能动作 |
|---|---|
| 平均文件远小于目标大小 | Rewrite Data Files |
| Delete Files 数持续增长 | Rewrite Data Files，应用 deletes |
| Manifest 数过多、规划变慢 | Rewrite Manifests |
| Snapshot 数和 metadata log 持续增长 | Expire Snapshots |
| 存储中有大量未引用旧文件 | 审计后 Remove Orphan Files |
| 高频谓词仍扫描大量同分区文件 | 评估 sort order / clustering |
| 单个分区持续过热 | 评估 partition evolution |

推荐流程：

```text
采集表级指标
    ↓
挑选真正需要维护的表和分区
    ↓
小批量 rewrite，限制并发和单次范围
    ↓
验证查询与提交结果
    ↓
按保留策略 expire snapshots
    ↓
以更长安全窗口清理 orphan files
```

不建议每天无差别重写整张表。维护本身会消耗扫描、Shuffle、写 I/O，并与在线 Writer 竞争提交。

## 十二、性能问题的分层诊断

```text
第一层：规划
Manifest 是否太多？谓词是否下推？规划出多少文件？

第二层：数据布局
分区是否有效？文件是否太小？统计范围是否过宽？Delete 是否太多？

第三层：执行引擎
Scan Task 是否均衡？是否发生 Shuffle？是否有倾斜和资源瓶颈？

第四层：提交
Catalog 延迟如何？是否频繁 CAS 冲突？commit retry 是否耗时？

第五层：维护
compaction 是否追得上写入？expiration 是否兼顾所有 Reader？
```

不要只通过增大 executor memory 解决 Iceberg 表布局问题，也不要只通过 compaction 解决一个错误 Join 导致的 Spark Shuffle 问题。

## 十三、常见误解

### Schema Evolution 会修改旧 Parquet Schema

通常只更新 Iceberg 元数据。Reader 通过 field id 和当前 Schema 解释旧文件。

### Partition Evolution 后旧数据也自动按新规则分区

旧文件不变，只是新旧 specs 可以同时被正确规划。

### Snapshot 越多，数据就被复制越多份

Snapshot 主要复用不可变文件和元数据树。额外存储来自发生变化后仍被历史引用的旧文件以及新增元数据。

### Expire Snapshots 等于删除所有旧文件

只有不再被任何有效 Snapshot、branch 或 tag 引用的文件才可删除。

### Remove Orphan Files 可以设很短时间实时运行

过短窗口可能删除尚未提交的有效写入文件，是高风险配置。

## 十四、最终心智模型

表演进与表维护分别回答两个问题：

```text
Evolution
从下一个写入开始，Schema、Partition、Sort 应该是什么？

Maintenance
已经积累的 Data Files、Delete Files、Manifests 和 Snapshots
怎样重新组织与安全清理？
```

Iceberg 允许先通过元数据演进保持业务连续，再按成本和 SLA 异步整理历史文件。这种“逻辑立即生效、物理逐步优化”的解耦，是大规模湖表能够长期演进的关键。
