# ETL 入门：从数据搬运到可运营的数据管道

上一篇调研列出了很多工具和协议，但第一次接触数据工程时，最容易困惑的是：这些词分别解决什么问题？它们之间是什么关系？本文先建立一张“地图”，再解释关键术语。

## 1. 先用一个电商例子理解 ETL

假设一家电商有三个系统：

- 订单系统：MySQL，保存订单、商品和支付状态；
- 行为系统：Kafka，持续产生浏览、点击、加购事件；
- 客服系统：一个提供 REST API 的 SaaS。

业务希望每天早上看到销售报表，并且让客服 Agent 能回答“某个客户最近买过什么”。一个典型数据管道是：

```text
MySQL / Kafka / SaaS API
        │
        │ Extract：读取数据或读取变化
        ▼
Raw 原始区（保留原貌、批次、位点）
        │
        │ Transform：清洗、关联、聚合、脱敏
        ▼
Silver 明细层 → Gold 指标层 / 客户画像
        │
        ├── Load 到数仓或 Iceberg 湖表，供报表查询
        └── Load 到检索库，供 Agent 查询
```

ETL 不只是“写一段脚本搬数据”。生产系统还必须知道：搬到哪里了、搬到哪一条了、失败后从哪里继续、重复运行会不会重复写入、源表改字段后会不会把下游弄坏。

## 2. 一张术语关系图

```text
Source ──Connector/Tap──▶ Extract ──▶ Transform ──▶ Load ──▶ Sink/Destination
                              │             │             │
                              └── State/Offset/Checkpoint ─┘

Pipeline/DAG ──由── Scheduler/Orchestrator 调度
       │
       ├── Worker 执行 Task/Job
       ├── Quality 检查数据
       ├── Lineage 记录来源和去向
       └── Observability 记录日志、指标、告警
```

### 2.1 Pipeline、Job、Task、DAG

- **Pipeline（管道）**：从源到目标的一整条处理链，例如“订单库 → 数仓 → 报表”。
- **Task（任务）**：管道中的一个动作，例如下载文件、执行 SQL、刷新索引。
- **Job（作业）**：一次可执行的处理单元；不同工具对 Job 的边界定义略有不同。
- **DAG（Directed Acyclic Graph，有向无环图）**：用依赖关系描述任务执行顺序。`抽取 → 清洗 → 聚合` 是 DAG；“无环”表示不能出现任务 A 等 B、B 又等 A 的死循环。
- **Scheduler（调度器）**：决定什么时候运行、哪些任务可以并行、失败后如何重试。
- **Orchestrator（编排器）**：比调度器更完整，通常还管理依赖、参数、运行状态、回填、告警和人工审批。Airflow、Dagster、Prefect、Kestra 都属于这一类。
- **Worker（执行器）**：真正运行 Python、SQL、Spark、Flink 或容器的进程/节点。编排器负责“安排”，Worker 负责“干活”。

不要把 Airflow、Spark、Airbyte 当成同一种工具：Airflow 主要编排，Spark 主要计算，Airbyte 主要连接和复制数据；它们经常组合使用。

## 3. Extract：数据从哪里来

### 3.1 Source、Destination、Connector

- **Source（源）**：数据被读取的一端，如 MySQL、API、文件、Kafka。
- **Destination/Sink（目标/接收端）**：数据写入的一端，如 PostgreSQL、ClickHouse、S3、Iceberg、向量数据库。
- **Connector（连接器）**：知道某个源或目标的协议、认证、分页、类型映射和错误处理的适配程序。

连接器是 ETL 产品最有价值、也最难维护的部分。API 改字段、数据库权限变化、限流策略变化，都会让连接器失效。

### 3.2 全量、增量和 CDC

- **全量（Full Load）**：每次把整个表或整个数据集重新读取。简单但耗时、耗流量，适合首次同步或小表。
- **增量（Incremental Load）**：只读取上次之后新增或修改的记录。常依据 `updated_at`、递增 ID 或文件修改时间。
- **CDC（Change Data Capture，变更数据捕获）**：读取数据库的 WAL、binlog、redo log 等日志，捕获 insert/update/delete。Debezium 和 Flink CDC 是常见开源实现。
- **Snapshot（快照）**：某一时刻数据的完整视图。CDC 通常先做一次快照，再继续消费日志。

增量同步必须保存进度：

- **Bookmark/Watermark（水位）**：上次已处理到的时间、ID 或日志位点。
- **Offset（偏移量）**：消息系统中的位置，例如 Kafka 的 partition offset。
- **State（状态）**：连接器为了断点续传而保存的 JSON 或数据库记录，可能包含多个 stream 的 bookmark。
- **Checkpoint（检查点）**：计算引擎定期保存的可恢复状态；失败时从最近检查点继续。

水位不是业务时间本身。现实中可能有迟到事件、时钟偏差和事务提交延迟，所以应记录“源端发生时间”和“处理时间”，并设计重放窗口。

## 4. Transform：数据如何变得可用

常见转换包括：

- **清洗**：去除非法值、统一编码、处理 null、纠正时间和金额类型。
- **映射（Mapping）**：把 `user_id` 映射成 `customer_id`，或把多个来源的字段统一成一个规范名称。
- **Join（关联）**：按主键或业务键把订单和客户表拼起来。大表 Join 会消耗大量内存和网络，需要分区、排序或广播策略。
- **聚合（Aggregation）**：按天、客户、商品计算销售额、次数、平均值。
- **窗口（Window）**：对一段时间内的数据计算，例如“最近 5 分钟点击数”。流处理中常见滚动窗口、滑动窗口和会话窗口。
- **脱敏（Masking）**：隐藏手机号、身份证等 PII（个人敏感信息）。
- **规范化（Normalization）**：把嵌套 JSON 或 API 响应拆成适合表存储的结构。

### 4.1 Schema、数据契约和 schema evolution

- **Schema（模式）**：数据的结构和类型，例如列名、类型、是否可空、主键和嵌套结构。
- **Data Contract（数据契约）**：生产者与消费者约定的 schema、语义、质量和变更规则。
- **Schema Registry**：集中保存事件 schema 的服务，通常还检查兼容性。
- **Schema Evolution（模式演进）**：数据结构随业务变化。增加可空字段通常较安全；删除字段、改类型、修改主键会影响下游。

数据契约至少应写清楚：字段含义、单位和时区、主键、删除语义、允许的 null、版本号、向后/向前兼容策略。只给一份示例 JSON 不能算契约。

## 5. Load：数据应该放在哪里

### 5.1 OLTP、OLAP、数仓、数据湖、Lakehouse

- **OLTP（Online Transaction Processing）**：在线事务库，擅长少量记录的快速读写，例如订单库 MySQL/PostgreSQL。
- **OLAP（Online Analytical Processing）**：分析库，擅长扫描大量列并聚合，例如 ClickHouse、Trino、DuckDB。
- **Data Warehouse（数据仓库）**：结构化、治理较强的分析存储，通常由数据库提供 SQL 查询。
- **Data Lake（数据湖）**：把原始文件放在对象存储上，格式可以很多，成本低但治理要求高。
- **Lakehouse（湖仓）**：在数据湖文件之上增加表、事务、schema 演进、时间旅行等能力。Iceberg、Hudi、Delta Lake 属于开放表格式，不等于底层文件本身。

### 5.2 Bronze、Silver、Gold

这是常见的分层命名，不是强制标准：

- **Bronze/Raw（原始层）**：尽量保留源数据原貌，加上 `ingested_at`、来源和批次信息，便于审计和回放。
- **Silver（明细层）**：完成类型统一、去重、基础清洗和标准化。
- **Gold（服务层/指标层）**：面向报表、推荐或 API 的业务指标和宽表。

分层的价值是把“原始事实”和“业务解释”分开，业务规则变化时不必重新访问已经消失的源数据。

## 6. 批处理和流处理

| 概念 | 批处理 | 流处理 |
| --- | --- | --- |
| 数据边界 | 有限（bounded）数据集 | 无限（unbounded）事件流 |
| 触发方式 | 定时、手动、文件到达 | 持续消费或事件触发 |
| 常见工具 | Spark、dbt、DuckDB | Flink、Kafka Streams、Spark Structured Streaming |
| 难点 | 回填、长任务、资源峰值 | 状态、乱序、迟到、背压和一致性 |

- **Event time（事件时间）**：事件在源系统实际发生的时间。
- **Processing time（处理时间）**：ETL 看到并处理事件的时间。
- **Watermark（事件时间水位）**：系统认为某个时间点之前的事件大部分已到达，可以推进窗口计算。
- **Late event（迟到事件）**：事件时间较早但到达较晚的事件，可能触发窗口修正。
- **Backpressure（背压）**：下游处理太慢，上游被迫放慢或积压，防止内存无限增长。
- **Stateful processing（有状态处理）**：计算需要记住历史，例如每个用户累计金额、窗口中已有的计数。Flink 通过 checkpoint/savepoint 保证这类状态可恢复。

## 7. 可靠性：至少一次、至多一次、恰好一次

- **At-most-once（至多一次）**：消息可能丢，但不会重复。适合允许少量丢失的监控数据。
- **At-least-once（至少一次）**：尽量不丢，但失败重试可能重复。业务系统最常见。
- **Exactly-once（恰好一次）**：在定义好的边界内，结果看起来只生效一次；通常需要 checkpoint、事务提交和幂等 sink 的共同配合，不能只看工具宣传。
- **Idempotency（幂等）**：同一个操作执行一次或多次，最终结果相同。常见做法是使用业务主键 + 事件版本 upsert，或先写 staging 再原子替换。
- **Deduplication（去重）**：按事件 ID、主键和版本去掉重复消息。
- **Dead-letter queue（死信队列）**：无法解析或违反契约的记录被隔离，等待人工修复，而不是阻塞整条管道。
- **Replay（回放）**：从原始区或消息日志重新执行某个时间范围，修复错误转换或重建下游。

工程上通常选择“至少一次传输 + 幂等写入”，比追求端到端恰好一次更容易落地。

## 8. 常见数据格式和协议

### 8.1 文件与内存格式

- **CSV**：人和工具都容易读，但没有可靠的类型、转义和嵌套结构约束。
- **JSON/JSONL**：API 和日志常用；JSONL 每行一个对象，适合流式处理。
- **Parquet**：列式文件，压缩和分析扫描效率高，是湖仓中最常见的分析文件格式之一。
- **Avro**：schema 与二进制数据配套，适合消息和长期存储；读取时需要正确的 writer/reader schema。
- **Arrow**：跨语言的列式内存布局和 IPC，适合 Python、Java、Go、Rust 等程序之间交换表格数据。

“文件格式”和“表格式”不是一回事：Parquet 描述一个文件怎么存，Iceberg 描述一张表由哪些文件组成、当前 schema 是什么、如何原子提交快照。

### 8.2 数据库和消息协议

- **SQL**：关系数据查询和转换的共同语言。
- **JDBC/ODBC**：应用或 ETL 连接关系数据库的标准接口；驱动由数据库厂商或社区提供。
- **REST/HTTP/JSON**：SaaS API 抽取的默认组合，但分页、限流和认证语义由服务方定义。
- **Kafka topic/partition/offset**：topic 是逻辑事件流，partition 提供并行和有序范围，offset 标记消息位置。
- **Consumer group**：一组消费者共同消费 topic；同一 partition 在同一组内通常只分给一个消费者。
- **Kafka Connect**：Kafka 生态的 source/sink 运行时，连接器把外部系统接入 Kafka。

### 8.3 Singer、Airbyte Protocol 和 SeaTunnel API

这些是“某个连接器生态的内部标准”，不是所有 ETL 都通用：

- **Singer**：tap（抽取器）通过 stdout 输出 `SCHEMA`、`RECORD`、`STATE` JSONL，target（加载器）从 stdin 读取。它的优势是简单、可用 Unix pipe 组合。
- **Airbyte Protocol**：Airbyte 连接器与平台之间的消息和状态约定，适合 Airbyte 运行时。
- **SeaTunnel Source–Transform–Sink API**：把连接器接口与执行引擎解耦，同一个连接器可以映射到不同引擎。

选协议时先问“需要跨哪个生态复用”，而不是寻找一个并不存在的“万能 ETL 协议”。

## 9. 数据质量、血缘、目录和可观测性

- **Data Quality（数据质量）**：检查完整性、唯一性、范围、及时性、 referential integrity（引用完整性）和分布变化。质量检查应成为发布门禁，而不是失败后才手工运行。
- **Data Lineage（数据血缘）**：回答“这张报表/字段来自哪些源，经过哪些任务”。OpenLineage 用 Job、Run、Dataset、Facet 描述运行级血缘。
- **Data Catalog（数据目录）**：记录资产名称、schema、负责人、标签、质量和使用说明，帮助人和 Agent 找到正确数据。
- **Observability（可观测性）**：日志告诉你发生了什么，指标告诉你变化趋势，trace 告诉你一次运行跨过哪些组件。数据系统还应监控新鲜度、吞吐、延迟、积压和成本。
- **Audit（审计）**：记录谁在什么时候用什么版本代码读取/修改了哪些数据，尤其适用于 PII 和 Agent 自动写入场景。

## 10. Agent ETL 为什么是一个新问题

传统 ETL 的目标是报表、数仓和业务系统；Agent ETL 的目标通常是“让模型获得新鲜、可检索、可追溯的上下文”。它增加了几层处理：

```text
文档/代码/数据库
    ↓ 抽取、解析、切分
规范化文本与元数据
    ↓ embedding / entity extraction
向量库、图数据库或搜索索引
    ↓ MCP/API/受限工具
Agent 检索、引用和行动
```

关键概念：

- **Embedding（嵌入）**：把文本转换为向量，使相似内容在向量空间中靠近。
- **Vector database（向量数据库）**：按向量相似度检索，常与关键词搜索混合。
- **Chunk（文本块）**：文档被切成可检索的小片段；切得过小会丢上下文，过大则检索不精确。
- **RAG（Retrieval-Augmented Generation）**：先检索相关资料，再把资料放入提示词生成答案。
- **MCP（Model Context Protocol）**：让 Agent 以约定方式调用工具和读取资源；它是工具接入协议，不是 ETL 引擎，也不会自动解决权限问题。
- **Incremental indexing（增量索引）**：只重新解析发生变化的文档、记录或代码，避免每次重新 embedding 全库。

CocoIndex、dlt、Airbyte Agents、Superglue 等项目的共同方向，是把“连接数据”和“维护 Agent 上下文”变成可重复、可观测的流水线。生产环境仍要增加最小权限、人工审批、提示注入防护、版本化和回滚。

## 11. 用一套最小例子串起所有概念

每天凌晨运行一次“订单日报”：

1. **Scheduler** 触发一个 **DAG**。
2. **Connector** 从 MySQL 按 `updated_at` 读取增量，保存 **bookmark**。
3. 把原始 JSONL 写入 **Bronze**，带上 `batch_id` 和 `ingested_at`。
4. Spark/dbt 执行 **Transform**：类型转换、去重、Join 客户表、计算销售额。
5. Great Expectations 检查订单 ID 唯一、金额非负、当天数据量没有异常下降。
6. 通过事务或幂等 upsert 写入 **Gold** 表；失败记录进入死信区。
7. OpenLineage 记录这次 **Run** 的输入 Dataset、输出 Dataset 和代码版本。
8. 仪表盘展示耗时、行数、延迟和失败原因；需要时从 Bronze **Replay**。

如果再增加客服 Agent，只需把 Gold 客户画像和订单摘要增量同步到搜索/向量库，并通过受限 MCP 工具让 Agent 查询，而不是把数据库管理员权限直接交给模型。

## 12. 建议的学习顺序

1. 先掌握 SQL、主键/外键、事务、索引和基本数据建模。
2. 用 Python + dlt 或 Meltano/Singer 完成一个 API → PostgreSQL 的小管道。
3. 学会全量/增量、bookmark、幂等 upsert 和 schema 演进。
4. 用 dbt Core 或 DuckDB 做清洗、Join、聚合和数据质量检查。
5. 再学习 Airflow/Dagster/Prefect 的 DAG、重试、回填和监控。
6. 需要实时性时学习 Kafka 的 partition/offset/consumer group，再进入 Flink/CDC。
7. 最后学习 Parquet、Iceberg、OpenLineage，以及面向 Agent 的增量索引和 MCP 权限治理。
