# Trino 内存、容错与性能诊断

Trino 通过流水线和内存计算降低查询延迟，但 Hash Join、聚合、排序、窗口、Exchange Buffer 和并发查询都可能消耗大量内存。默认执行模式下，中间结果没有形成可供任意 Worker 重用的持久边界，因此 Worker 失败通常会使 Query 失败。

本文把内存、Blocked、Spill、Fault-tolerant Execution、Resource Group 和性能诊断放在同一条运行链路中理解。

## 一、先看一个容易出问题的查询

```sql
SELECT c.region,
       o.product_id,
       sum(o.amount) AS total_amount,
       row_number() OVER (
           PARTITION BY c.region
           ORDER BY sum(o.amount) DESC
       ) AS rn
FROM iceberg.sales.orders o
JOIN iceberg.sales.customers c
  ON o.user_id = c.user_id
WHERE o.order_date >= DATE '2026-01-01'
GROUP BY c.region, o.product_id;
```

它可能同时产生：

- 大范围数据扫描；
- Join build-side Hash Table；
- 按 Join Key 的 Exchange；
- 高基数聚合状态；
- 按 region 的窗口排序；
- 多个 Stage 的输入输出 Buffer。

如果集群还有许多查询并发运行，单条 SQL 看起来没有超过整机内存，也可能因为多个 Query、Task 和 Driver 竞争而失败。

## 二、Worker 内存花在什么地方

```text
Worker JVM Heap
├── Trino 跟踪的查询内存
│   ├── Join Hash Table
│   ├── Aggregation State
│   ├── Sort / Window Buffer
│   ├── Exchange / Output Buffer
│   ├── Page / Block
│   └── Connector Reader / Writer 中被跟踪的内存
│
└── Heap Headroom
    ├── JVM 和框架对象
    ├── 未被 Trino 内存上下文跟踪的分配
    └── GC、安全余量等
```

Trino 的内存限制主要用于协调查询资源，不能简单等同于 JVM `-Xmx`：

```text
JVM Heap
  ≠ 某一条 Query 可以全部使用的内存
  ≠ 所有内存都被 Trino 查询内存统计完整覆盖
```

`memory.heap-headroom-per-node` 会为未跟踪分配和 JVM 运行保留空间。查询内存上限与 Headroom 配置不合理时，即使 Trino 统计中的查询内存看似安全，进程仍可能遭遇 GC 压力或 OOM。

## 三、哪些 Operator 最容易消耗内存

### 3.1 Hash Join

Build side 需要构建 Hash Table：

```text
build rows
    ↓
Join Key + payload + hash/index 结构
    ↓
常驻内存，等待 probe side
```

Broadcast Join 会让每个参与 Worker 保存完整 build side；Partitioned Join 让每个 Worker 保存一个分区。统计信息低估 build side 是常见内存风险。

### 3.2 Hash Aggregation

`GROUP BY` 通常需要为每个不同 key 保存聚合状态。数据量大但 key 少时，Partial Aggregation 很有效；数据量大且 key 几乎唯一时，Hash Table 会持续增长。

### 3.3 Sort、Top-N 和 Window

全局排序需要收集并比较大量数据；Top-N 可以只保留部分候选，但 N 很大时仍会占内存。窗口函数可能要为一个 partition 保存、排序大量行。

### 3.4 Exchange Buffer

Stage 之间的数据通过有界 Buffer 传输。Buffer 太小可能降低吞吐，太大则会占用更多 Worker Heap；高并发查询会放大总量。

### 3.5 Connector

文件解码、字典、解压缩、远程读取缓冲和写入缓冲也会占用资源。Connector 是否正确报告和限制内存，会影响 Trino 的全局判断。

## 四、Blocked 不等于线程卡死

Trino Operator 不能继续执行时会返回阻塞状态，让调度线程去运行其他可执行工作，而不是一直占用线程空转。

常见等待关系：

```text
TableScan       → 等待远端数据或文件读取
Join probe      → 等待 build-side Hash Table
Exchange source → 等待上游 Page
Exchange sink   → 等待下游释放 Buffer
Memory request  → 等待可用内存
Output          → 等待 Client 拉取结果
```

因此：

- CPU Time 高：确实花了大量时间计算；
- Scheduled Time 高：Task 获得了较多调度时间；
- Blocked Time 高：大量时间在等待某个条件；
- Wall Time 高但 CPU 低：优先检查 I/O、Exchange、内存或 Client 消费。

Blocked 是异步流水线的正常组成部分，关键是看阻塞原因和持续时间。

## 五、查询内存限制为什么必要

如果没有限制，一条异常查询可以占满所有 Worker Heap，使其他 Query 无法运行，甚至让集群进程崩溃。

常见限制维度包括：

- 单个 Query 在单节点的内存；
- 单个 Query 在整个集群的总内存；
- 包含可撤销内存后的更高层总量；
- Resource Group 的软内存和并发限制。

达到限制后的结果可能是：

```text
等待内存
    ↓ 仍无法释放
触发 Low-memory Killer 或查询内存限制
    ↓
终止某个 Query / Task 尝试
```

仅仅提高查询内存上限不一定解决问题，还可能让一个错误计划影响更多并发查询。应先确认是数据量确实需要、Join 策略错误、统计失真、数据倾斜，还是过滤没有下推。

## 六、Spill 到磁盘解决什么

Spill 允许部分支持的 Operator 把可撤销的中间数据写到本地磁盘，以降低当前内存占用：

```text
内存中的 Join / Aggregation / Sort 数据
        ↓ 内存被回收
本地 Spill 文件
        ↓ 需要时重新读取
继续计算
```

它以磁盘 I/O、序列化和更长延迟换取完成更大查询的机会。需要注意：

- 不是所有 Operator 和 Join 类型都支持 Spill；
- Spill 不能保证任意大查询都成功；
- 数据重新读回时仍必须有足够内存处理一个分块；
- Spill 磁盘饱和会让查询甚至整个节点变慢；
- 当前官方文档把传统 Spill 标为 legacy，建议大型批查询优先评估 Task Retry 的 Fault-tolerant Execution。

所以 Spill 是内存压力的缓冲手段，不是修复坏 SQL、错误统计和数据倾斜的万能开关。

## 七、默认执行为什么难以重试单个 Task

Trino 默认通过 Worker 内存 Buffer 和网络流水传输 Exchange 数据：

```text
上游 Task 产生 Page
        ↓
下游 Task 边接收边处理
        ↓
中间结果没有完整、持久地保存
```

如果一个 Worker 在查询中途退出：

- 该 Worker 上运行的 Task 消失；
- 它内存中的 Exchange Buffer 和中间状态消失；
- 下游可能已经消费了其中一部分数据；
- 上游输入和其他 Stage 也可能仍在变化。

缺少可复用的持久中间结果时，单独补跑一个 Task 很难保证完整衔接，因此默认通常让整个 Query 失败，由 Client 或用户重新提交。

这与 Spark 默认会保存 Shuffle 文件并依据 Lineage 重算失败分区的思路不同。

## 八、Fault-tolerant Execution 怎样工作

Fault-tolerant Execution（FTE）为查询或 Task 重试增加可恢复边界。核心变化是把 Exchange 数据 spool 到外部存储：

```text
Stage A Tasks
    ↓ 写入
Exchange Manager
    ↓ S3 / 兼容对象存储 / HDFS 等
持久化的中间分区
    ↓ 读取
Stage B Tasks
```

当 Worker 失败时，新 Worker 可以重新执行失败部分，并复用已经完成的 Exchange 输出。

### 8.1 QUERY Retry

```properties
retry-policy=QUERY
```

Worker 故障后重新尝试整个 Query。它适合以大量较小查询为主、希望自动恢复瞬时节点故障的场景。

### 8.2 TASK Retry

```properties
retry-policy=TASK
```

只重试失败的 Task 尝试，更适合长时间、大规模批查询。Task Retry 必须配置 Exchange Manager，因为其他 Task 要能够重新读取已经完成的中间输出。

FTE 的边界：

- 它不会修复 SQL 语法、权限、坏数据等确定性错误；
- Connector 必须支持查询重试，尤其要保证读取或写入语义正确；
- 外部 Exchange 会增加存储 I/O、成本和延迟；
- 大批查询与短交互查询常常适合使用不同集群或工作负载配置。

## 九、Spill 与 FTE 不是一回事

| 维度 | Spill | Fault-tolerant Execution |
|---|---|---|
| 主要目标 | 缓解某个 Operator 的内存压力 | Worker/Task 失败后自动恢复查询 |
| 存储位置 | 通常是 Worker 本地磁盘 | Exchange Manager 管理的共享外部存储 |
| 数据用途 | 当前 Operator 稍后重新读回 | 失败后供其他 Task/Worker 重用 |
| 是否提供 Task Retry | 不提供 | `TASK` 策略提供 |
| 当前定位 | Legacy 内存扩展手段 | 大型查询推荐评估的容错执行模式 |

二者都可能把中间数据写出内存，但目的、生命周期和恢复能力不同。

## 十、Resource Group 解决什么

Worker 被多个用户和 Query 共享，仅有单查询内存上限还不够。Resource Group 可以按用户、来源、Query 类型或其他选择规则，对工作负载进行排队和资源分配。

```text
global
├── adhoc
│   ├── BI
│   └── analyst
└── pipeline
    ├── ETL
    └── scheduled-report
```

一个 Query 只属于一个叶子 Resource Group，同时消耗该组及其父组资源。常见控制包括：

- `maxQueued`：最多排队多少 Query；
- `hardConcurrencyLimit`：最多同时运行多少 Query；
- `softMemoryLimit`：组内查询可使用的软内存额度；
- 调度策略和权重；
- CPU 和物理扫描数据量限制。

Resource Group 主要保护集群公平性和稳定性。它不能把一个本身低效的 Query 自动优化好，而是避免这条 Query 无限制挤占其他工作负载。

## 十一、统计信息怎样影响资源使用

CBO 依赖 Connector 提供的表和列统计信息。估算会影响：

```text
Join 顺序
Build / Probe 选择
Broadcast / Partitioned Join
部分聚合和其他优化决策
```

典型连锁问题：

```text
统计信息认为 customers 只有 20 MB
        ↓
选择 Broadcast Join
        ↓
实际过滤后有 5 GB
        ↓
每个 Worker 构建 5 GB Hash Table
        ↓
内存不足或严重 GC
```

所以排查 Join 内存问题时，既要看实际大小，也要比较计划估算与 `EXPLAIN ANALYZE` 的实际行数。

## 十二、一次查询慢的分层诊断

不要一开始就调整 JVM 或 Exchange 参数。先定位慢在哪一层。

### 12.1 Client 与排队

- Query 是否长时间处于 `QUEUED`；
- Resource Group 是否达到并发或内存限制；
- Client 是否缓慢获取结果；
- 大结果是否让 Coordinator 传输成为瓶颈，是否适合 Spooling Protocol。

### 12.2 Planning

- SQL 是否包含大量 Join、UNION 或展开表达式；
- Catalog/Metastore 响应是否慢；
- Iceberg/Hive 表是否有海量小文件和分区；
- Coordinator CPU、Heap 和 GC 是否异常；
- 是否生成了过多 Split、Stage 或 Task 描述。

### 12.3 Scan

- 物理输入字节是否远大于最终需要的数据；
- Predicate、Projection、分区和文件剪枝是否生效；
- Split 是否过多、过小；
- 对象存储、HDFS 或数据库吞吐是否成为限制；
- JDBC 数据源是否被过多并发读取压垮。

### 12.4 Exchange

- 跨 Stage 的网络字节是否异常大；
- Filter 和 Partial Aggregation 是否发生在 Exchange 前；
- Worker 网络是否饱和；
- 是否有大量输出 Buffer 堵塞；
- FTE 外部 Exchange Storage 是否慢。

### 12.5 Join 与聚合

- Join 分布是否合理；
- build side 实际大小是否符合估算；
- Dynamic Filter 是否生效；
- Group By 或 Join Key 是否倾斜；
- 少数 Task 是否形成明显长尾。

### 12.6 内存与 GC

- Query 内存是集中在某个 Stage 还是全局都高；
- 哪个 Operator 占用最多；
- Worker Heap 与 Headroom 是否合理；
- 是否频繁 Full GC；
- Spill/FTE 是否产生磁盘或对象存储瓶颈。

## 十三、优先使用哪些观察工具

### 13.1 EXPLAIN

用于确认优化后的静态计划：

```sql
EXPLAIN (TYPE DISTRIBUTED)
SELECT ...;
```

看 Remote Exchange、Join 分布、Scan 约束和聚合层次。

### 13.2 EXPLAIN ANALYZE

用于比较估算与真实执行：

```sql
EXPLAIN ANALYZE
SELECT ...;
```

看每个 Fragment/Operator 的输入输出行数、CPU、Scheduled 和 Blocked。它会真实执行 SQL，不适合无评估地用于高成本写操作或超大查询。

### 13.3 Web UI 与监控

Web UI 适合观察 Query、Stage 和 Task 的实时状态；JMX/Prometheus 等监控适合观察集群长期趋势。需要同时关注：

- 查询队列、并发和失败率；
- Coordinator Planning 延迟和 Heap；
- Worker CPU、Heap、GC 和节点丢失；
- 输入、Exchange、Spill/FTE 存储吞吐；
- Task 输入分布和长尾。

## 十四、常见故障对应什么范围

| 故障 | 默认模式 | 启用合适 FTE 后 |
|---|---|---|
| SQL 语法/权限错误 | Query 失败 | 仍失败，不应重试 |
| Worker 进程退出 | Query 通常失败 | 可按 QUERY 或 TASK 策略重试 |
| Coordinator 退出 | 其管理的 Query 通常丢失 | 不能仅靠 Task Retry 解决 Coordinator 生命周期问题 |
| 数据源暂时超时 | 取决于 Connector 和错误类型 | 可能重试，但取决于 Connector 支持 |
| 确定性坏数据 | Query 失败 | 重试通常仍会失败 |
| 查询超过内存限制 | Query/Task 尝试失败 | FTE 不是无限内存，仍需调整计划或资源 |

容错执行降低的是瞬时基础设施故障造成的重跑成本，不会把所有失败都转化为成功。

## 十五、与 Spark 容错和内存对照

| 维度 | Spark | Trino 默认模式 | Trino FTE Task Retry |
|---|---|---|---|
| 主要工作负载 | 通用批处理/流处理 | 低延迟 SQL | 大型批量 SQL |
| 中间结果 | Shuffle 文件等 | 内存/网络流水 Exchange | 外部存储 Spooling Exchange |
| Worker 失败 | 重算相关 Task/Stage | Query 通常失败 | 重试失败 Task |
| 内存压力 | Spill、Shuffle、Executor 内存管理 | 查询限制、内存阻塞、Legacy Spill | 更细 Task + 外部 Exchange |
| 工作进程共享 | Executor 属于 Application | Worker 被多个 Query 共享 | Worker 被多个 Query 共享 |

## 十六、最终心智模型

```text
查询先通过 Resource Group 获得运行资格
        ↓
Coordinator 依据统计信息选择计划
        ↓
Worker 用内存执行 Join / Aggregation / Sort
        ↓
无法继续时 Operator 进入 Blocked，而不是无限占用线程
        ↓
超过资源边界时查询可能失败或被终止
        ↓
传统 Spill 用本地磁盘缓解部分内存压力
        ↓
FTE 用外部 Exchange 建立可重试边界
        ↓
诊断时沿 Queue → Planning → Scan → Exchange → Operator → Memory 分层定位
```
