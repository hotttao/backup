# 第7章：持久状态的实践

## 本章核心

流处理程序通常要运行很久，不能假设机器永不故障，也不能假设所有输入未来都能重新读取。因此，状态必须被可靠保存，并且要在正确性、恢复成本和存储成本之间平衡。

## 1. 为什么需要持久状态

持久状态主要解决两件事：

- **正确性**：输入已经被源端消费、无法重新获取时，仍保留继续计算所需的中间结果。
- **效率**：失败后从最近检查点恢复，避免从头重放所有输入和重复计算。

有界输入常可以整体重跑，所以历史上的批处理系统倾向于少保存中间状态；无界输入不能无限重跑，因此状态、检查点和状态清理会成为核心能力。

## 2. 隐式状态

### 原始分组

`GroupByKey` 将同一个 key 和窗口下的全部输入保存为列表，再在触发时计算结果。它简单、通用，但会保存大量原始数据，并且每次重新触发都可能重复扫描和聚合。

### 增量组合

对求和、计数、平均值等聚合，只保留紧凑的累加器：

```python
class Average:
    def create_accumulator(self):
        return (0, 0)  # sum, count

    def add_input(self, acc, value):
        return (acc[0] + value, acc[1] + 1)

    def merge(self, a, b):
        return (a[0] + b[0], a[1] + b[1])

    def output(self, acc):
        return acc[0] / acc[1]
```

如果组合操作满足交换律和结合律，就可以增量计算、局部预聚合并行化，显著减少状态和网络数据。Flink 的窗口聚合、状态后端和本地聚合都体现了这个思想。

## 3. 通用显式状态

有些业务无法用一个简单聚合器表示，例如广告转化归因：访问、曝光和目标事件可能乱序到达，需要等待一段事件时间后，沿着引用链寻找匹配的曝光。

这类逻辑通常需要：

- `MapState`：保存 URL 到访问记录、源目标组合到曝光记录的映射。
- `SetState`：保存待处理的目标集合。
- `ValueState`：保存最早待归因目标的时间戳。
- `Timer`：在事件时间达到条件后触发归因。

伪代码：

```python
def process(event, state, timer_service):
    if event.is_visit:
        state.visits[event.url] = event
    elif event.is_impression:
        state.impressions[event.source_target] = event
    elif event.is_goal:
        state.pending_goals.add(event)
        timer_service.register_event_time(event.time)

def on_timer(timestamp, state):
    for goal in state.pending_goals_before(timestamp):
        trail = trace_referer_chain(goal, state.visits)
        impression = find_impression(trail, state.impressions)
        if impression:
            emit_attribution(impression, trail, goal)
        state.pending_goals.remove(goal)
```

这里的关键不是 API 名称，而是三个自由度：状态数据结构可以按业务选择，读写粒度可以按性能选择，处理时机可以由事件时间和计时器选择。

## 4. 状态生命周期与 Flink 实践

状态不能无限增长，需要结合窗口结束、水位、允许迟到时间和业务 TTL 清理。工程上还要关注：

- checkpoint/savepoint 是否覆盖算子状态和位点；
- 状态后端是内存、磁盘还是嵌入式 KV 存储；
- 状态序列化格式是否兼容升级；
- 热 key 是否导致单个 key 的状态过大；
- 定时器和状态是否会因水位停滞而长期不清理。

## 一句话总结

持久状态是流处理正确恢复和高效运行的基础；简单聚合用增量状态，复杂业务用 keyed state + timer，并必须设计状态清理策略。
