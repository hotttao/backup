# 第3章：水位 Watermark

> 水位是流式系统最重要、也最容易误解的概念之一。本章重点解释“它是什么、不能保证什么、如何传播，以及它如何影响窗口输出”。

## 1. 为什么需要水位

事件时间窗口按事件发生时间组织数据，但事件到达顺序可能完全不同。系统面对事件时间窗口 `[10:00, 11:00)` 时，必须决定什么时候可以输出结果：

```text
事件时间：10:05、10:50、10:20
处理顺序：10:05 → 10:50 → 10:20
```

看到 10:50 的事件，并不能证明 10:00～11:00 的所有事件都已到达，因为 10:20 的事件可能还在路上。水位就是系统对“事件时间进展程度”的估计。

## 2. 水位的定义

可以把水位 `W` 理解为一个事件时间下界：

```text
当 Watermark = 10:50 时，系统认为事件时间早于 10:50 的数据基本已经观察到。
```

更准确地说，水位是一个启发式进度指标，不是全世界所有数据都已到达的数学证明。水位通常单调递增，不应向后退。

水位与窗口结束时间的关系：

```text
窗口结束时间 = 11:00
当 Watermark >= 11:00
→ 系统可以认为窗口接近完整
→ 触发窗口的最终计算/输出
```

注意：水位 11:00 并不意味着永远不会再有事件时间早于 11:00 的数据到达，只代表系统按既定策略认为继续等待的收益已经很低，或者输入源提供了足够的进度保证。

## 3. 水位解决的不是延迟，而是推断

处理时间延迟回答“系统现在处理到哪里”；水位回答“按事件时间看，系统认为数据已经推进到哪里”。

```text
处理时间：现在是 12:00
事件时间：水位推进到 11:00
含义：系统在 12:00 时认为 11:00 之前的数据大体已到齐
```

水位让系统可以在无界、乱序数据中做出窗口关闭和状态清理决策。

## 4. 源水位的创建

水位通常从数据源开始创建。源需要根据已观察到的事件时间、输入分片或分区的进度，产生自己的水位。

概念伪代码：

```python
class Source:
    def __init__(self):
        self.max_event_time_seen = None

    def on_event(self, event):
        self.max_event_time_seen = max(
            self.max_event_time_seen or event.event_time,
            event.event_time,
        )
        emit(event)

    def current_watermark(self):
        # 允许一定的乱序和迟到
        return self.max_event_time_seen - allowed_lateness
```

但真实系统不能简单对全局最大事件时间做减法。一个源可能有多个分区，其中一个分区已经推进到 12:00，另一个分区仍停留在 10:30。如果只看前者，水位会推进过快；因此通常需要按分区维护进度，再取所有活跃分区的最小值。

## 5. 多分区源的水位

```python
def source_watermark(partition_watermarks):
    active = [w for w in partition_watermarks if w is not None]
    if not active:
        return MIN_TIMESTAMP
    return min(active)
```

直觉是：只要还有一个输入分区可能产生更早的数据，整个源就不能安全地把全局水位推进到更晚。

这会带来一个重要现象：一个停滞或异常的分区可能拖住整个输入源的水位，导致窗口迟迟不关闭。因此生产系统还要考虑空闲分区检测、分区失效和动态分区变化。

## 6. 水位如何在算子之间传播

一个算子可能有多个输入。为了避免下游过早关闭窗口，通常采用保守传播：

```python
def operator_watermark(input_watermarks):
    return min(input_watermarks)
```

例如 Join 算子同时接收订单流和支付流：

```text
订单流水位：12:00
支付流水位：11:20
Join 水位：11:20
```

因为支付流仍可能补充 11:20 之后、但早于 12:00 的匹配数据。取最小值可以避免丢失潜在关联。

对于无数据或已标记空闲的输入分区，系统可以不再让它拖住水位；但空闲判断必须谨慎，否则会过早推进水位。

## 7. 水位与窗口触发

窗口通常同时受两类时间控制：

- 事件时间边界：决定事件属于哪个窗口；
- 水位进度：决定窗口何时可以触发最终计算。

```python
class WindowOperator:
    def __init__(self, window_end):
        self.window_end = window_end
        self.state = []

    def on_event(self, event):
        if event.event_time < self.window_end:
            self.state.append(event)

    def on_watermark(self, watermark):
        if watermark >= self.window_end:
            result = aggregate(self.state)
            emit_final(result)
            clear_state()
```

这个模型说明：事件到达时负责把数据放入正确窗口，水位到达时负责推动窗口生命周期。

## 8. 水位不是数据完整性的绝对保证

必须区分三个概念：

1. 水位：系统对事件时间进度的推断。
2. 完整性：某个窗口是否真的不会再有相关数据。
3. 触发：系统决定何时输出一次结果。

水位可以帮助系统在工程上估计完整性，但不能保证现实世界中没有极晚到达的数据。计费、财务等场景通常需要额外的修订、对账或人工定义的截止时间。

## 9. 百分位数水位

简单的最大事件时间减固定延迟，无法适应事件时间偏差不断变化的数据。百分位数水位会根据观测到的事件时间延迟分布，选择某个百分位作为进度估计。

例如，选择 99% 分位数意味着系统试图覆盖大多数延迟情况，但仍可能有约 1% 的数据晚于估计。它的优点是比固定延迟更能适应动态输入，缺点是需要统计数据分布，而且仍然是近似方法。

## 10. 处理时间水位

有些场景只关心系统观察数据的进度，不关心事件真实发生时间，此时可以使用处理时间水位。它更容易推进，也更容易判断窗口是否关闭，但不能处理严重的事件时间乱序。

```text
处理时间窗口：数据到达后 5 分钟关闭
事件时间窗口：水位超过窗口结束时间后关闭
```

## 11. 水位停滞与异常

水位长时间不推进，常见原因包括：

- 某个输入分区没有数据但未标记空闲；
- 某个分区消费失败或网络阻塞；
- 上游事件时间本身停止推进；
- 多输入算子使用最小水位，被慢输入拖住；
- 水位生成策略过于保守。

诊断时需要同时观察各分区水位、算子输入水位、窗口状态数量、迟到数据量和消费延迟。

## 12. 水位传播伪代码

```python
class WatermarkTracker:
    def __init__(self, input_count):
        self.input_watermarks = [MIN_TIMESTAMP] * input_count
        self.output_watermark = MIN_TIMESTAMP

    def update_input(self, input_id, watermark):
        self.input_watermarks[input_id] = max(
            self.input_watermarks[input_id],
            watermark,
        )

        # 多输入算子保守地取最小值，并保证单调递增
        candidate = min(self.input_watermarks)
        if candidate > self.output_watermark:
            self.output_watermark = candidate
            emit_watermark(self.output_watermark)
```

## 13. 本章最终理解

```text
事件时间：数据属于哪个时间
处理时间：系统什么时候看到数据
水位：系统认为事件时间推进到哪里
窗口：按时间把无界数据切成有限区域
触发器：什么时候计算/输出窗口结果
迟到数据：水位之后仍到达的旧事件
```

一句话：水位不是“数据已经全部到齐”的证明，而是流式引擎用来推进事件时间、关闭窗口、清理状态和平衡延迟与完整性的进度信号。
