# 第10章：大规模数据处理的演进

## 本章核心

现代流处理不是凭空出现的，而是多个系统逐步贡献了可扩展性、开源生态、低延迟、乱序处理、持久日志、统一模型和可移植性。

## 1. 主要系统的贡献

| 系统 | 关键贡献 | 局限或下一步需求 |
|---|---|---|
| MapReduce | 用简单的 map/reduce API 隐藏分布式扩展和容错 | Map → Shuffle → Reduce 结构较刚性 |
| Hadoop | 开源实现和生态，推动 Pig、Hive、HBase 等发展 | 以批处理为主，延迟较高 |
| Flume | 高级可组合流水线、自动优化、融合和组合器提前 | 最初主要服务批处理 |
| Storm | 让低延迟流处理广泛普及 | 常以至多一次/至少一次换取低延迟，强一致性不足 |
| Spark | RDD 和内存计算；Spark Streaming 用微批处理无界数据 | 早期流语义受微批模型限制，对乱序和低延迟需继续演进 |
| MillWheel | 持久状态、计时器、水位、精确一次，解决乱序处理 | 主要是谷歌内部系统 |
| Kafka | 持久、可重放的日志；强化流和表思想 | 日志本身不等于完整的流计算语义 |
| Cloud Dataflow | 把 Flume 的优化流水线与 MillWheel 的乱序语义统一 | 需要可移植的开放实现 |
| Flink | 将乱序事件时间处理、状态快照和保存点带入开源生态 | 复杂状态和运维仍需工程治理 |
| Beam | 统一批流编程模型、SDK、DSL 和运行引擎适配层 | 可移植模型与各引擎能力仍有差异 |

## 2. 演进主线

可以把历史看成几条能力逐步叠加：

1. MapReduce 解决“如何在大集群上做计算”。
2. Hadoop 让这套思想进入开源生态。
3. Flume、Dataflow 让逻辑流水线与物理执行计划解耦，并自动优化。
4. Storm 提供低延迟，但暴露了低延迟与强一致之间的冲突。
5. MillWheel、Flink 引入状态、计时器、水位和检查点，开始系统性处理乱序事件。
6. Kafka 让流具有持久性和可重放性。
7. Beam 尝试把批流语义和运行时能力抽象成可移植模型。

## 3. 对选择 Flink 的启示

Flink 的核心价值不只是“速度快”，而是把事件时间、水位、状态、计时器、检查点和保存点组合成了一个完整的流处理运行时。理解这些理论后，才能正确判断窗口何时关闭、迟到数据如何修正、状态何时清理以及故障恢复后结果为何仍然正确。

## 一句话总结

流处理的演进方向，是从“能扩展地处理数据”逐步走向“能以低延迟、强一致、可恢复、可解释地处理乱序无界数据”。
