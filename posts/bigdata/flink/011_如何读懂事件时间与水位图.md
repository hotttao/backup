# 如何读懂事件时间与水位图

> 本文结合《流式系统》图 3-7，解释坐标轴、数据点、输入/输出水位，以及窗口输出时间戳对下游结果的影响。

## 一、图的整体流程

图中有两条上游数据流：

```text
Frank 的移动设备得分
    → 会话窗口
    → 会话长度 ─┐
                 ├→ 合并 → 2 分钟固定窗口 → 平均会话长度
Julie 的控制台得分
    → 会话窗口
    → 会话长度 ─┘
```

左上和右上计算每个玩家的会话长度，下方把两路会话长度放入 2 分钟固定窗口，再计算平均值。

---

## 二、坐标轴和图中元素

### 2.1 横轴：事件时间

事件时间 Event Time 表示业务事件实际发生的时间。

某个得分在 12:03 产生，它的横坐标就是 12:03，无论系统什么时候收到它。

### 2.2 纵轴：处理时间

处理时间 Processing Time 表示系统实际观察或处理该事件的时间。

```text
事件时间：12:03
处理时间：12:07

含义：事件发生 4 分钟后才被系统处理
```

处理时间从下向上推进，所以应该把图想成一段由下向上播放的动画。

### 2.3 灰色斜虚线

灰色斜线表示理想状态：

```text
事件时间 = 处理时间
```

数据点离斜线越远，事件到达系统的延迟通常越大。灰线不是 Watermark，也不是窗口边界。

### 2.4 彩色数据点

- 红色菱形：Frank 的移动设备得分事件；
- 蓝色方块：Julie 的控制台得分事件；
- 点的位置：横坐标是事件时间，纵坐标是处理时间；
- 点里的数字：游戏得分，不是时间。

### 2.5 顶部和底部的黑色标记

```text
顶部黑色标记
= 会话窗口输出的单个会话长度

底部黑色标记
= 2 分钟固定窗口内，会话长度的平均值
```

黑色标记的位置还表达两个时间：

- 横坐标：结果携带的输出事件时间；
- 纵坐标：结果实际物化的处理时间。

## 三、实线、虚线和黄色线

图例中的曲线分别表示：

| 曲线 | 含义 |
|---|---|
| 红色实线 | 移动设备阶段的输入水位 |
| 红色点状虚线 | 移动设备阶段的输出水位 |
| 蓝色实线 | 控制台阶段的输入水位 |
| 蓝色点状虚线 | 控制台阶段的输出水位 |
| 黄色实线 | 下游平均会话长度阶段的输入水位 |

输入水位表示上游告诉当前阶段的事件时间进度。

输出水位还要考虑当前阶段内部没有完成的窗口、状态和待发送结果：

```text
输出水位
= min(
    输入水位,
    阶段内部未完成工作所限制的时间戳
  )
```

因此输出水位通常不会领先于输入水位。

### 3.1 下游为什么取两路水位的最小值

下方算子同时接收移动端和控制台结果：

```text
移动端输出水位 = 12:07
控制台输出水位 = 12:05

下游输入水位 = min(12:07, 12:05)
               = 12:05
```

只要较慢分支还可能产生更早的正常数据，下游就不能提前关闭窗口。图中的黄色线就是两路上游输出水位的保守最小值。

## 四、怎样读取 Watermark 曲线

Watermark 是处理时间 p 的函数：

```text
W(p) = 处理时间为 p 时，系统认为已经完成到的事件时间
```

由于图把事件时间放在横轴、处理时间放在纵轴，应该使用两种读法。

### 4.1 固定处理时间，横着看

在某个处理时间画水平线，水平线与 Watermark 的交点横坐标，就是该时刻的事件时间进度。

```text
固定 y = 处理时间
读取交点 x = 当前 Watermark
```

交点越靠右，事件时间进度越先进。

### 4.2 固定窗口结束时间，竖着看

在某个事件时间画竖线，竖线与 Watermark 的交点纵坐标，表示 Watermark 大约什么时候越过该时间。

```text
固定 x = 窗口结束时间
读取交点 y = 窗口可触发的处理时间
```

### 4.3 为什么输入水位一开始是曲线

输入水位不是某条 record 的运动轨迹，而是数据源进度 W(p) 的连续示意。

数据源启动后可能正在消费积压，不同分区、消息到达速度和乱序程度也在变化，所以 Watermark 不会匀速前进：

```text
曲线接近竖直
→ 处理时间过去较多，事件时间只前进一点
→ 水位推进慢

曲线接近水平
→ 很短处理时间内，事件时间前进很多
→ 水位快速追赶
```

Flink 实际发送的是离散 Watermark 控制记录。更新足够密集时，书中把许多细小阶梯连接成曲线，以突出总体趋势。

### 4.4 为什么输出水位是阶梯虚线

```text
竖直段：
处理时间继续增长
但窗口或状态还没完成
Watermark 被固定在同一事件时间

水平段：
阻塞解除
Watermark 在很短处理时间内向右跳
```

输入源持续更新进度，所以实线较平滑；窗口经常经历“等待—输出”，所以输出水位更像阶梯。

## 五、会话窗口怎样动态形成

假设 session gap 为 1 分钟。系统并不是一开始就知道会话最终覆盖 [12:02,12:05)，而是随事件动态扩展：

```text
收到 12:02:00
→ 候选会话 [12:02:00,12:03:00)

收到 12:02:40
→ 窗口重叠
→ 合并为 [12:02:00,12:03:40)

收到 12:03:30
→ 扩展为 [12:02:00,12:04:30)

收到 12:04:00
→ 扩展为 [12:02:00,12:05:00)
```

相邻事件的间隔没有达到 1 分钟，会话就继续延长。

当输入 Watermark 越过当前会话结束位置时，系统认为不会再有按时事件继续扩展该会话，于是触发窗口。

因果关系是：

```text
上游持续处理数据
→ 输入 Watermark 前进

新事件到达
→ 会话结束位置可能延后

输入 Watermark 越过最终结束位置
→ 会话关闭并输出
```

不是“会话变长，所以 Watermark 跟着变大”。输入 Watermark 由上游整体进度决定；会话只会限制当前算子的输出 Watermark。

## 六、窗口输出时间戳为什么影响 Watermark

窗口结果也必须携带事件时间戳，才能进入下游事件时间窗口。可选择：

- 会话窗口结束位置；
- 第一个非迟到事件时间；
- 其他有业务意义的事件时间。

未完成窗口可以理解为对输出 Watermark 设置了保持点：

```text
output watermark
= min(input watermark, 未完成工作的时间戳保持点)
```

### 6.1 使用窗口结束位置

会话最终为 [12:02,12:05)：

```text
保持点接近 12:05
输入 Watermark = 12:04

output watermark = min(12:04,12:05)
                 = 12:04
```

保持点位于输入水位前方，输出水位可以基本跟随输入水位推进。

### 6.2 使用第一个事件时间

同一个会话仍为 [12:02,12:05)，但输出时间戳选择 12:02：

```text
保持点 = 12:02
输入 Watermark = 12:04

output watermark = min(12:04,12:02)
                 = 12:02
```

窗口尚未结束，输出水位会一直被卡在约 12:02。等输入 Watermark 越过 12:05、窗口完成输出，保持点被删除，输出水位才向右跳。

输出时间戳因此会改变：

1. 当前阶段输出水位的推进速度；
2. 下游输入水位；
3. 窗口结果进入下游哪个事件时间窗口；
4. 下游窗口何时触发；
5. 下游最终聚合结果。

Watermark 已经越过后才到达的旧事件不会让水位倒退，而是按 allowed lateness、late trigger、结果更新或丢弃策略处理。

## 七、为什么第一个平均会话长度是 1.0

这里有两层窗口：

```text
第一层：session gap = 1 分钟
作用：计算每个会话的长度

第二层：fixed window = 2 分钟
作用：计算每两分钟内会话长度的平均值
```

固定窗口 [12:00,12:02) 的宽度虽然是 2 分钟，但下游不是计算固定窗口自身的长度，而是在平均它收到的“会话长度”。

### 7.1 Frank 第一个会话为什么是 1.0

Frank 的第一个事件发生在约 12:00.x：

```text
一个事件创建候选会话：
[12:00.x,12:01.x)

1 分钟 gap 内没有后续事件与它连接
→ 会话不再延长
→ 会话长度 = 1.0 分钟
```

这里必须区分两层窗口：`[12:00.x,12:01.x)` 是第一层的**会话窗口**，`[12:00,12:02)` 是第二层的**固定窗口**。它们不是同一个窗口。

```text
第一层：会话窗口
事件时间约为 12:00.x
session gap = 1 分钟
→ 候选会话约为 [12:00.x,12:01.x)
→ 上游输入 Watermark 越过约 12:01.x
→ 会话关闭，输出“会话长度 = 1.0”
→ 该输出的事件时间取会话结束位置，约为 12:01.x

第二层：2 分钟固定窗口
收到事件时间约为 12:01.x、值为 1.0 的会话结果
→ 这个结果属于 [12:00,12:02)
→ 下游输入 Watermark 越过 12:02
→ 固定窗口关闭，输出 avg([1.0]) = 1.0
```

| 被触发的窗口 | Watermark 需要越过的位置 | 输出 |
|---|---|---|
| Frank 的第一个会话窗口 | 约 `12:01.x` | 会话长度 `1.0` |
| 下游固定窗口 `[12:00,12:02)` | `12:02` | 平均会话长度 `1.0` |

因此，不能说“第一个会话的区间是 `[12:00,12:02)`，水位也推进到 `12:02`”。准确说法是：第一个会话约为 `[12:00.x,12:01.x)`；它产生的结果落入下游的 `[12:00,12:02)`，后者要等下游 Watermark 越过 `12:02` 才输出。

严格实现中，窗口输出时间戳可能表示为窗口结束前的最大时间戳，例如 `windowEnd - 1ms`；这里用“约为窗口结束位置”建立直觉即可。

### 7.2 上游 Watermark 是怎样推进的

这里的“上游 Watermark”是指**会话窗口算子收到的输入 Watermark**。它通常由数据源根据已观察到的事件时间和乱序策略产生，不是由会话窗口主动推进的。

例如，系统允许事件最多乱序 10 秒，可以近似理解为：

```text
Watermark = 当前观察到的最大事件时间 - 10 秒
```

| 新到达事件的时间 | 已观察到的最大事件时间 | Watermark（近似值） |
|---|---|---|
| 12:00:20 | 12:00:20 | 12:00:10 |
| 12:00:50 | 12:00:50 | 12:00:40 |
| 12:01:30 | 12:01:30 | 12:01:20 |
| 12:02:00 | 12:02:00 | 12:01:50 |

假设 Frank 的事件时间为 `12:00:15`，它创建候选会话 `[12:00:15,12:01:15)`。当后续事件使上游 Watermark 推进到 `12:01:20` 时：

```text
输入 Watermark 12:01:20 > 会话结束时间 12:01:15
→ 会话窗口触发
→ 输出会话长度 1.0
```

因此，因果顺序是：

```text
后续事件到达
→ 数据源观察到更大的事件时间
→ 数据源生成更大的 Watermark
→ Watermark 沿数据流传到会话窗口算子
→ Watermark 越过会话结束时间
→ 会话窗口触发
```

Watermark 不必恰好停在窗口结束时间，它可以从 `12:00:40` 直接推进到 `12:01:20`。`12:01:15` 只是触发该会话的门槛。

如果数据源有多个并行分区，下游算子的输入 Watermark 通常取所有活跃输入分区的最小值：

```text
分区 A Watermark = 12:02
分区 B Watermark = 12:01
分区 C Watermark = 12:03

算子输入 Watermark = min(A, B, C) = 12:01
```

因此，一个长时间没有数据的分区可能卡住整体 Watermark。Flink 可以将这种分区标记为 idle，使它暂时不参与最小值计算。

> Watermark 表示上游对事件时间进度的判断。会话窗口负责使用 Watermark 判断何时触发，不负责凭空推进 Watermark。

### 7.3 Julie 的 1.6 为什么不参与第一个平均值

图 3-7 使用会话结束位置作为输出事件时间。Frank 的 1.0 位于 12:02 之前，而 Julie 的 1.6 已位于 12:02 之后。

固定窗口采用左闭右开区间：

```text
[12:00,12:02) 不包含 12:02
[12:02,12:04) 包含 12:02
```

所以第一个固定窗口中只有一个值：

```text
[12:00,12:02) → [1.0]
平均值 = 1.0
```

前四个结果可以核对为：

| 固定窗口 | 会话长度 | 平均值 |
|---|---|---:|
| [12:00,12:02) | 1.0 | 1.0 |
| [12:02,12:04) | 1.6、1.0 | 1.3 |
| [12:04,12:06) | 1.0、2.9 | 约 2.0 |
| [12:06,12:08) | 1.8 | 1.8 |

顶部黑色数字是第一层产生的会话长度；底部黑色数字是第二层产生的平均值。底部结果通常画在固定窗口结束位置附近，例如位于 12:02 附近的 1.0，代表窗口 [12:00,12:02) 的输出。

## 八、映射到 Flink

这张图使用通用流处理和 Apache Beam 风格描述。Flink 的名称和内部实现不完全相同，但核心关系一致。

### 8.1 事件时间和源 Watermark

```java
WatermarkStrategy
    .<Event>forBoundedOutOfOrderness(Duration.ofSeconds(10))
    .withTimestampAssigner((event, timestamp) -> event.eventTime);
```

TimestampAssigner 决定数据点横坐标；WatermarkStrategy 决定源事件时间进度。

### 8.2 多输入取最小进度

Flink 多输入算子的 Watermark 通常受所有活跃输入通道中的最小值限制。空闲输入可通过 idleness 策略避免永久拖住整体 Watermark。

### 8.3 Watermark 触发事件时间窗口

```python
def on_watermark(watermark):
    for window in windows:
        if watermark >= window.end:
            emit(aggregate(window.state))
```

实际边界可能使用 windowEnd - 1ms 等内部表示，理解时可以先记为“Watermark 越过窗口结束位置后触发”。

Flink 的 Watermark 是带内控制记录，会和数据一起沿通道传播。算子收到 Watermark 后，先完成该进度触发的定时器和窗口处理，再把可推进的 Watermark 传给下游。

## 九、最终读图口诀

```text
横轴：事件在业务时间上属于哪里
纵轴：系统现实中什么时候处理它
彩色点：原始事件
顶部黑色点：单个会话长度
底部黑色点：固定窗口内会话长度的平均值
实线：阶段输入水位
点状虚线：考虑未完成工作后的输出水位
黄色线：两个上游输出水位的最小值
灰色斜线：事件时间等于处理时间的零延迟参考
```

阅读动作：

```text
固定处理时间，横着看
→ 交点横坐标是当前 Watermark

固定窗口结束时间，竖着看
→ 交点纵坐标是窗口可触发的处理时间
```

会话窗口、Watermark 和输出时间戳之间的关系：

```text
事件到达 → 会话可能扩展
上游推进 → 输入 Watermark 前进
Watermark 越过会话结束 → 会话触发
输出时间戳 → 决定未完成会话把输出 Watermark 卡在哪里
```
