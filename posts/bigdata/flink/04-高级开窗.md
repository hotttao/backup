# 第4章：高级开窗

## 1. 处理时间开窗

处理时间开窗按系统观察到数据的时间组织窗口，优点是实现简单、窗口容易关闭、无需等待乱序数据。它适合监控吞吐、系统健康度等“现在看到了什么”的场景。

缺点是事件延迟会改变数据归属。设备离线、网络中断或跨地域传输会让事件到达时间与发生时间差异很大，因此处理时间窗口可能把事件放入错误的时间段。

## 2. 事件时间开窗回顾

事件时间窗口按事件实际发生时间分组，需要水位推进窗口结束，并允许迟到数据对已输出结果进行修订。它更符合业务事实，但代价是状态保存时间更长、需要处理迟到和结果更新。

## 3. 会话窗口

会话窗口是动态窗口：同一个 Key 的事件如果在一段时间内持续活跃，就属于同一会话；当不活跃时间超过超时阈值，当前会话关闭。

```python
def session_window(events, gap):
    events = sorted(events, key=lambda e: e.event_time)
    sessions = []
    current = []

    for event in events:
        if not current or event.event_time - current[-1].event_time <= gap:
            current.append(event)
        else:
            sessions.append(current)
            current = [event]

    if current:
        sessions.append(current)
    return sessions
```

在真正的流式系统中不能直接排序完整输入。**事件时间会话窗口**要依靠 Keyed State、事件时间和水位动态维护；**处理时间会话窗口**则依靠机器时钟关闭。迟到事件可能重新连接两个已经看似结束的事件时间会话，因此系统需要允许合并窗口或发出修订结果。

## 4. 自定义窗口

自定义窗口可以根据业务条件定义边界，例如：

- 每个用户独立的活动周期；
- 订单从创建到完成的生命周期；
- 某类事件触发开始，另一类事件触发结束；
- 事件数量达到阈值时关闭。

自定义窗口必须明确：窗口归属 Key、开始/结束条件、时间域、触发器、迟到策略、状态清理方式和结果更新语义。

## 5. 窗口不是单一概念

一个完整窗口定义至少包含：

```text
窗口分配：事件属于哪个窗口
窗口状态：窗口中暂存或聚合什么
触发条件：何时计算一次
累积模式：结果如何与历史输出关联
清理条件：何时删除状态
迟到策略：晚到数据如何处理
```

## 6. 本章重点

处理时间窗口简单但可能不符合业务事实；事件时间窗口正确但需要水位、状态和迟到数据处理；会话和自定义窗口则进一步把窗口边界交给数据和业务逻辑决定。

## 7. 开窗和水位到底是什么关系

可以先记住一句话：

> **窗口决定“哪些事件放在一起”，水位决定“系统认为时间推进到哪里、什么时候可以计算和清理”。**

二者不是同一个概念，也不是“水位决定事件属于哪个窗口”：

```text
事件时间戳 ──窗口分配器──▶ 事件属于 [0, 10) 还是 [10, 20)
水位线 ─────触发器/清理器▶ 窗口是否可以输出、是否允许继续修订
```

对一个 10 秒滚动事件时间窗口 `[0, 10)` 来说，事件时间为 `3` 的事件永远属于这个窗口，即使它在现实时间的第 30 秒才到达。水位只是对系统的一种判断：**时间戳小于等于某个值的事件，大概率已经到齐**。当水位超过窗口结束时间，窗口才可以触发计算；当水位超过“窗口结束时间 + 允许迟到时间”，窗口状态才可以清理。

因此，开窗和水位的因果链是：

1. 事件带着 `event_time` 到达；窗口分配器根据它的时间戳分配窗口。
2. 算子保存窗口状态，例如窗口内的计数和金额。
3. 水位不断推进，触发器观察水位是否越过窗口结束边界。
4. 水位越过边界后输出结果；如果配置了 allowed lateness，窗口还会暂时保留。
5. 清理时间到达后删除状态，之后再来的旧事件只能被丢弃或送入侧输出。

## 8. 一个完整的 10 秒窗口例子

假设我们统计每 10 秒的订单金额，允许乱序 5 秒，允许窗口结果在首次输出后再修改 5 秒。事件按“到达顺序”如下：

| 到达时刻 | 事件时间 | 金额 | 当时水位 `max_event_time - 5s` | 发生的事 |
| ---: | ---: | ---: | ---: | --- |
| 1s | 1s | 10 | -4s | 放入 `[0,10)`，还不能关闭窗口 |
| 2s | 7s | 20 | 2s | 仍在 `[0,10)` |
| 8s | 3s | 15 | 2s | 乱序到达，但仍属于 `[0,10)` |
| 12s | 12s | 30 | 7s | 放入 `[10,20)`；`[0,10)` 仍未关闭 |
| 20s | 14s | 25 | 9s | 水位还没到 10s，`[0,10)` 仍等待 |
| 25s | 16s | 40 | 11s | 水位越过 10s，输出 `[0,10)`：金额 `45` |
| 26s | 8s | 12 | 11s | 这是迟到事件；窗口尚未清理，更新结果为 `57` |
| 30s | 20s | 50 | 15s | 水位越过 `10s + 5s`，清理 `[0,10)` 状态 |

这个例子体现了三个容易混淆的点：

- 第 3 行的事件虽然比第 2 行晚到，但因为 `event_time=3`，仍然归入 `[0,10)`；窗口归属看事件时间，不看网络到达顺序。
- 第 6 行水位变成 11s，才说明 `[0,10)` 基本等齐，于是第一次输出 45。水位不是“又产生了一条数据”，而是时间进度信号。
- 第 7 行虽然已经输出过，但在允许迟到期内仍可修订结果。下游必须能处理 update/upsert，不能只支持 append-only。

如果第 8 行的 `event_time=8` 在水位已经超过 15s、窗口状态被清理后才到达，它就不能再更新 `[0,10)`，通常会被丢弃或发送到 side output（迟到数据流）。

## 9. 水位是怎么生成的

常见策略是“当前观察到的最大事件时间减去最大乱序时长”：

```text
watermark = max_seen_event_time - out_of_orderness
```

例如最大乱序时长为 5 秒，当前见过的最大事件时间是 20 秒，则水位大约是 15 秒。它不是精确真相，而是一个有业务取舍的估计：

- 乱序时长设得太小：窗口更快输出，但迟到事件更多；
- 乱序时长设得太大：结果更完整，但延迟、状态大小和资源占用更高。

在并行消费 Kafka 等多分区数据时，算子通常取各分区水位的最小值：

```text
operator_watermark = min(partition_1_watermark, partition_2_watermark, ...)
```

这是因为只要有一个分区还可能产生旧事件，整体窗口就不能贸然关闭。某个分区长期没有数据时，水位可能被它“卡住”，因此需要配置 **idle source detection（空闲分区检测）**，让系统暂时忽略确认已经空闲的分区。

## 10. 会话窗口中的水位

会话窗口没有固定的结束时间。设会话间隔为 10 分钟，某个用户最后一个事件的事件时间是 10:05，那么这个会话理论上的结束时间是 10:15。系统不能在看到 10:05 后立即关闭，因为事件可能乱序到达；要等水位超过 10:15，才有较大把握认为该会话结束。

如果之后又收到事件时间为 10:10 的事件，它会把会话结束时间推迟到 10:20；如果两个原本分开的会话被迟到事件连接起来，Flink 还可能合并窗口并发出修订结果。因此会话窗口比固定窗口更依赖水位、allowed lateness 和窗口合并语义。

## 11. Flink 代码中的对应位置

下面是表达关系的简化代码（重点是概念，不是完整作业）：

```python
events \
    .assign_timestamps_and_watermarks(
        # 事件时间戳 + 最大乱序 5 秒，生成 watermark
        WatermarkStrategy.for_bounded_out_of_orderness(seconds=5)
    ) \
    .key_by(lambda e: e.user_id) \
    .window(TumblingEventTimeWindows.of(Time.seconds(10))) \
    .allowed_lateness(Time.seconds(5)) \
    .aggregate(sum_amount)
```

其中：

- `assign_timestamps_and_watermarks` 负责从事件中提取时间戳并生成水位；
- `TumblingEventTimeWindows.of(10s)` 负责定义窗口边界和事件归属；
- `allowed_lateness(5s)` 负责窗口首次触发后还保留多久；
- `aggregate` 负责计算窗口内的业务结果。

处理时间窗口没有事件时间和水位的等待过程，因为它直接按机器当前时间切分；这也是它延迟低但可能把“晚到的旧事件”算进错误时间段的原因。

## 12. 实际设计时先回答四个问题

1. **按什么时间分组？** 事件时间还是处理时间？
2. **最多允许多大的乱序？** 这个值决定水位推进速度。
3. **结果输出后还能不能修改？** 能修改就要设计 upsert、撤回或更新消息。
4. **什么时候删除状态？** 由窗口结束时间和 allowed lateness 共同决定，不能只看第一次输出。

把这四个问题回答清楚，就能理解大多数 Flink 开窗代码：窗口负责业务时间范围，水位负责等待边界，允许迟到负责修订窗口，清理时间负责控制状态成本。

## 13. 按开窗方法分别看：水位是否参与、如何参与

前面的例子使用的是**事件时间滚动窗口**，容易让人误以为所有窗口都依赖水位。更准确的模型是：

```text
Source
  └─ 时间戳分配器 + WatermarkStrategy（通常每个分区一条水位）
       └─ KeyBy
            └─ Window Assigner（决定事件进入哪些窗口）
                 └─ Trigger（决定何时计算）
                      └─ State / 清理定时器
```

水位生成通常发生在窗口之前，因此同一条流上的多个窗口可以共享同一条水位；但每一种窗口的边界和触发器不同，使用水位的方式也不同。

### 13.1 处理时间滚动窗口和滑动窗口：不需要水位

处理时间窗口使用 TaskManager 所在机器的当前时间：

- 滚动窗口 `[10:00:00, 10:00:10)` 到 10:00:10 时由处理时间定时器触发；
- 滑动窗口每隔 slide 周期由处理时间定时器触发；
- 事件晚到时，系统只看“什么时候被算子看到”，不会回到过去的事件时间窗口重新归档。

所以这两种窗口**不使用事件时间水位**。即使上游生成了 watermark，处理时间触发器也不会用它来关闭窗口。它的优点是低延迟、简单，缺点是网络延迟会改变统计结果。

处理时间会话窗口同理：用户超过 gap 时间没有新事件，按机器时钟关闭会话，而不是等待 watermark。

### 13.2 事件时间滚动窗口：水位越过固定结束边界

以 10 秒滚动窗口为例：

```text
[00, 10)  [10, 20)  [20, 30)
```

事件归属只由 `event_time` 决定；当 watermark `>= 10` 时，`[00,10)` 的 event-time trigger 才触发。若允许迟到 5 秒，窗口通常到 watermark `>= 15` 才清理。

这里水位的作用是“等待边界”，不是“重新分桶”：事件时间为 3 的事件无论何时到达都属于 `[00,10)`，只是到达太晚时可能已经无法修改结果。

### 13.3 事件时间滑动窗口：同一水位触发多个重叠窗口

窗口大小 10 秒、滑动步长 5 秒时：

```text
[00,10)  [05,15)  [10,20)  [15,25)
```

事件时间为 7 的事件会同时进入 `[00,10)` 和 `[05,15)`。水位生成方式并没有因为滑动窗口而改变，仍然是上游时间戳和乱序策略的结果；但是窗口会为每个结束边界注册 event-time timer：

- watermark 到 10，触发 `[00,10)`；
- watermark 到 15，触发 `[05,15)`；
- watermark 到 20，触发 `[10,20)`。

因此滑动窗口比滚动窗口保存更多状态，但二者使用的是同一条水位推进信号。

### 13.4 事件时间会话窗口：水位越过动态结束时间

会话窗口没有预先固定的 `[00,10)` 边界。gap 为 10 分钟时：

```text
用户最后事件 event_time = 10:05
会话暂定结束时间 = 10:15
watermark > 10:15 后才有条件关闭
```

如果 watermark 还没有超过 10:15，又来了一个 event_time=10:10 的事件，会话结束时间被推迟到 10:20。如果迟到事件把两个会话连接起来，窗口还可能合并。由此可见：

- **水位生成方式**仍然可以是 `max_event_time - out_of_orderness`；
- **水位使用方式**变成“越过每个会话自己的动态结束时间”；
- **窗口状态管理**还要处理会话合并和结果修订。

### 13.5 计数窗口：通常不需要水位

计数滚动窗口（每 100 条事件计算一次）和计数滑动窗口（每来 10 条事件滑动一次）由事件数量触发：

```text
收到第 100 条 → 触发一次
```

它们通常不需要 event-time watermark，也没有“等时间到齐”的语义。代价是无法直接表达“每 10 秒”这类时间业务规则，并且迟到事件只能按到达顺序计数。

也可以编写自定义 Trigger，把“达到 100 条”与“watermark 越过某个时间”组合起来。此时不是计数窗口天然需要水位，而是**自定义触发器选择使用了水位**。

### 13.6 全局窗口和自定义窗口：水位取决于 Trigger

Global Window 没有自动结束时间，所有事件默认进入同一个逻辑窗口，必须由自定义 Trigger 决定何时输出和清理：

- `CountTrigger`：按数量触发，不看 watermark；
- `ProcessingTimeTrigger`：按机器时钟触发，不看 watermark；
- `EventTimeTrigger`：按 watermark 触发；
- 组合 Trigger：可以同时等待数量、事件时间和外部信号。

所以“自定义窗口是否依赖水位”没有固定答案，应该检查它的 Trigger 和清理逻辑。

## 14. 水位推进方式到底是否一样

答案分两层：

### 14.1 水位的生成：通常与窗口类型无关

在同一个 Source 上，水位策略一般由事件时间戳和乱序容忍度决定，例如：

```text
watermark = 当前见过的最大事件时间 - 最大乱序时长
```

同一条流上同时开一个滚动窗口和一个滑动窗口，它们通常看到的是同一条算子水位，而不是各自重新计算一条水位。

但水位也不是全局唯一的：不同 Source、不同分区、不同乱序特征可以使用不同策略；并行输入通常取各分区水位的最小值，空闲分区还需要单独处理。

### 14.2 水位的使用：与窗口类型有关

| 窗口/触发方式 | 是否依赖 watermark | 水位具体做什么 |
| --- | --- | --- |
| 处理时间滚动/滑动/会话 | 否 | 使用机器时钟触发和清理 |
| 事件时间滚动 | 是 | 越过固定窗口结束时间后触发 |
| 事件时间滑动 | 是 | 依次越过多个重叠窗口的结束时间 |
| 事件时间会话 | 是 | 越过每个会话的动态结束时间，并可能触发合并 |
| 计数窗口 | 通常否 | 达到数量阈值就触发 |
| Global/自定义窗口 | 取决于 Trigger | 由自定义触发器决定是否监听水位 |

因此最准确的表述不是“开窗需要水位”，而是：

> **事件时间窗口通常用水位作为时间进度和触发依据；处理时间、计数窗口通常不用；自定义窗口由 Trigger 决定。水位怎么生成主要是 Source 问题，水位何时起作用才是窗口和 Trigger 的问题。**
