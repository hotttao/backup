# 第8章：流式 SQL

## 本章核心

流式 SQL 不是简单地给普通 SQL 加一个“实时”开关，而是要让 SQL 能表达随时间变化的关系，并正确处理窗口、水位、触发、更新和撤销。

## 1. 从关系到时变关系

传统关系是某个时间点的表快照；**时变关系（TVR）** 是一系列随时间演化的快照。对 TVR 应用过滤、投影、聚合等关系运算，仍然可以保持关系代数的闭包性质。

例如，用户得分不断到达时，`SUM(score) GROUP BY user` 的结果不是一次性表，而是不断被修正的表：Julie 的总分可能从 7 变成 8，再变成 12。

## 2. 流式 SQL 的两种输出

- **表语义**：查询当前状态或物化视图，关注“现在每个 key 的值是什么”。
- **流语义**：输出状态变化，记录新增、更新和撤销，关注“结果如何变化”。

一个更新后的结果可以表示为 changelog：

```text
+ (Julie, 7)       # 新值
- (Julie, 7)       # 撤销旧值
+ (Julie, 8)       # 新的当前值
```

如果只输出追加记录，消费者会把同一个业务结果误认为多个独立结果；更新流或撤销流因此非常重要。

## 3. Beam 模型与 SQL 的偏好

Beam 更偏向直接处理流，SQL 更偏向声明表。好的流式 SQL 应该隐藏不必要的复杂度，同时提供必要的显式能力：`TABLE`、`STREAM`、`TVR` 等输出选择，窗口定义，事件时间字段，以及水位和触发语义。

## 4. 水位、窗口和触发在 SQL 中的作用

- 窗口定义哪些事件被放入同一组；
- 水位表示系统对事件时间完整性的推断；
- 触发器定义什么时候把当前表状态物化成流；
- 累积模式定义多次结果如何被解释；
- 撤销记录让下游能够把旧值替换为新值。

典型语义是：当水位越过窗口结束时间后，发出该窗口的权威结果；在此之前也可以用处理时间或计数触发提前结果，迟到数据到达后再发更新。

## 5. 实际使用时的判断

写流式 SQL 前应先明确：输入是追加流还是更新流，结果是只允许最终值还是允许修正，使用事件时间还是处理时间，迟到数据如何处理，窗口状态何时清理，以及下游是否理解 changelog。

## 一句话总结

流式 SQL 的本质是：在时变关系上执行熟悉的关系运算，并用窗口、水位、触发器和撤销记录把结果变化可靠地交给下游。
